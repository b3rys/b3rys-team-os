# 프로젝트 종류별 하네스 구성

프로젝트를 열면 종류를 먼저 고르고, 그 종류의 역할표로 에이전트를 짠다. 역할 정의는 프로젝트 저장소의 `.claude/agents/<역할>.md` 에 파일로 고정한다(에이전트는 매번 새로 뜨므로 "구성" 은 파일이다). 짜는 법·품질 패턴·N 결정은 `b3os-harness-playbook` 이 정본이고, 여기는 ★종류별 역할표★만 둔다.

공통 규칙 (모든 종류)
- 오케스트레이터(담당 팀원)는 일을 직접 하지 않는다 — 순서 · 워크트리 · 병합 · 게이트 · 보고.
- 만든 사람과 판정하는 사람은 다르다. "통과" 는 검증 역할만 말한다.
- 산출은 파일로. 서브의 반환 텍스트는 보고가 아니라 데이터(JSON 한 줄).
- 병렬은 ★서로 다른 파일/소스★를 읽고 쓸 때만. 같은 파일을 둘이 고치면 병렬이 아니라 충돌이다.

## 앱·프로그램 개발 (예: Steno)

| 역할 | 수 | 도구 | 하는 일 |
| --- | --- | --- | --- |
| 아키 | 1 | 읽기만 | ★두 번★ — 착수 전 계약(메시지·필드·상태 주인·실패 동작·파일 소유), 통합 후 diff. ai-code-safety 기준 |
| 공통부 담당 | 1 (작업마다 겸임) | 읽기+쓰기 | 배선·프로토콜·공통 스타일·저장소처럼 ★모두가 건드리는 파일★의 유일한 쓰는 사람. 계약 변경을 먼저 기준 커밋에 넣는다 |
| 모듈 담당 | 각도 수만큼 | 읽기+쓰기(자기 워크트리) | 한 모듈 안 구현 + 단위 테스트. 공통부 파일은 쓰기 금지, 필요하면 `needs` 로 넘긴다 |
| 검증 | 1 | 읽기+쓰기(탐침·매니페스트만) | 통합된 같은 커밋에서 전체 동작 판정. 케이스→탐침→뮤턴트→인수 매니페스트 |

순서: 아키 계약 → 공통부 기준 커밋 → 모듈 병렬(기능 통합 브랜치 1 + 구현자별 하위 브랜치·워크트리) → 병합·번들 → 아키 diff ∥ 검증 → 고침 → 인수 게이트 → 릴리스.
공통부를 두는 이유: 아키의 계약만으로는 파일 충돌이 안 없어진다(Devon, 2026-09-14). 모듈 경계는 코드 구조를 따라 자른다 — 한 파일이 두 기능을 같이 배선하면 그 파일의 주인은 하나다.
떼기 어려운 작은 교차 수정은 한 구현자에게 같이 맡긴다. 파일 소유권 표와 인수 검사 영역 표는 별개다.

## 리서치 · 조사

| 역할 | 수 | 하는 일 |
| --- | --- | --- |
| 수집 | 소스 종류 수만큼 | 소스 하나씩(논문·코드·로그·DB·웹). 같은 반환 schema |
| 반증 | 1 | 수집된 주장마다 반대 근거를 찾는다. 살아남은 것만 넘긴다 |
| 종합 | 오케스트레이터 | 반증을 지난 것만으로 결론. 미검증은 미검증으로 표기 |

팬아웃 → 수집 → 적대검증 → 종합 형. N 은 소스 종류 수.

## 문서 · 슬라이드 · 보고서

## 인프라 · b3os 자체 변경

| 역할 | 수 | 하는 일 |
| --- | --- | --- |
| 영향 조사 | 호출부 종류 수만큼 | 호출부 · 스키마 · 스케줄러/훅 · 라이브 상태 각각 |
| 구현 | 1 | 워크트리 격리(`b3os-infra-safety`), 라이브 베이스 main 에 가드 먼저 |
| 검증 | 1 | 라이브가 아닌 사본에서 재현 → 양방향 뮤턴트 |

migration 레시피. 병렬은 조사 단계까지만 — 구현은 하나가 순서대로.

## 고르는 법
- 코드가 나오면 앱·프로그램. 결론이 나오면 리서치. 읽을 것이 나오면 문서. 팀 시스템이 바뀌면 인프라.
- 둘에 걸치면(예: 리서치 뒤 구현) 단계별로 종류를 바꿔 적용한다 — 한 하네스에 두 종류를 섞지 않는다.
