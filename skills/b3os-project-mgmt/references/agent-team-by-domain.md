# 도메인별 에이전트 팀 — 초기 설계와 진행 단계별 관리

프로젝트를 열 때 ★에이전트 팀을 설계★하고, 진행 단계마다 ★관리★(추가 · 역할 변경 · 해체)한다. 팀원 한 명이 서브에이전트를 여럿 띄워 일하므로, 팀 구성은 사람 조직이 아니라 ★그 팀원이 띄우는 역할의 표★다.

짜는 법 · 품질 패턴 · N 결정 · 런타임별 실행은 `b3os-harness-playbook` 이 정본이다 (③ 구조 규약, ⑤ 품질 패턴, `templates/recipes.md`). 여기는 ★어느 도메인에 어떤 역할을 두고, 단계마다 어떻게 바꾸나★만 둔다. codex·openclaw 팀원은 playbook ④ 런타임별 대응을 따른다.

## 1. 초기 설계 — 프로젝트를 열 때 한 번

어느 도메인이든 세 종류의 역할이 있어야 한다. 하나라도 없으면 하네스가 아니라 일꾼 여럿이다.

| 종류 | 역할 | 도구 | 이유 |
| --- | --- | --- | --- |
| 만드는 역할 | 도메인 전문 담당 N | 읽기+쓰기(자기 워크트리·자기 파일) | 각도 수만큼. 서로 ★다른 파일·소스★를 다룰 때만 병렬 |
| 판정하는 역할 | 검증 1 (+ 아키/감수 1) | 읽기만, 또는 검사물만 쓰기 | 만든 사람이 자기 것을 판정하지 않는다. "통과" 는 이 역할만 말한다 |
| 통합하는 역할 | 오케스트레이터 = 담당 팀원 | — | 일을 직접 하지 않는다. 순서 · 계약 · 병합 · 게이트 · 보고 |

공통부(모두가 건드리는 파일·자산)가 있으면 ★쓰는 사람을 1명★으로 못박는다. 계약(경계·형식·주인)만 정해서는 충돌이 안 없어진다.

설계 결과는 프로젝트 저장소에 파일로 남긴다:
- `.claude/agents/<역할>.md` — 역할마다 프론트매터(name · description · model · tools) + 입력/출력 프로토콜 · 에러 · 재호출 (playbook ③-2)
- `.claude/agents/README.md` — 역할표 + 파일(자산) 소유권 표 + 순서
- `TODO.md` 의 `🧱 정해진 구조` 절에 한 줄로 링크

### 도메인별 예시 (그대로 쓰지 말고, 각도 수와 자산 종류에 맞춰 줄이거나 늘린다)

**프로그램 개발** — 자산 = 코드. 판정 = 테스트·탐침·뮤턴트.

| 역할 | 수 | 하는 일 |
| --- | --- | --- |
| 아키 (읽기만) | 1 | 착수 전 계약(경계·필드·상태 주인·실패 동작·파일 소유) + 통합 후 diff. 코드 안전 기준 |
| 공통부 담당 | 1 (겸임) | 배선·프로토콜·공통 스타일·저장소의 유일한 쓰는 사람. 계약 변경을 먼저 기준 커밋에 |
| 모듈 담당 | 각도 수 | 한 모듈 구현 + 단위 테스트. 공통부 쓰기 금지, 필요하면 `needs` 로 |
| 검증 | 1 | 통합된 같은 커밋에서 전체 동작 판정. 케이스→탐침→뮤턴트→인수 매니페스트 |

순서: 계약 → 공통부 기준 커밋 → 모듈 병렬(기능 통합 브랜치 1 + 구현자별 하위 브랜치·워크트리, 같은 브랜치 공유 금지) → 병합 → 아키 ∥ 검증 → 고침 → 게이트 → 릴리스. 아키의 계약만으로는 파일 충돌이 안 없어진다 — 그래서 공통부 담당이 있다. 모듈 경계는 코드 구조를 따라 자른다(한 파일이 두 기능을 배선하면 주인은 하나).

**영상 제작** — 자산 = 대본·컷·소스·렌더. 판정 = 렌더 확인(사진·재생).

| 역할 | 수 | 하는 일 |
| --- | --- | --- |
| 기획·대본 | 1 | 스토리라인·컷 리스트(텍스트 먼저) |
| 소스 담당 | 소스 종류 수 (이미지·음성·자막·음악) | 컷 리스트대로 각자 생성. 저해상도 검증 → 고해상도 |
| 편집·합성 | 1 (공통부) | 타임라인은 한 사람만 만진다 |
| 검증 | 1 | 컷마다 대본 대조 + 렌더 재생 확인. 한글 텍스트는 렌더 사진으로 |

**콘텐츠 제작 (글·슬라이드·보고서·이미지)** — 자산 = 장·페이지. 판정 = 스펙 대조 + 렌더 사진.

| 역할 | 수 | 하는 일 |
| --- | --- | --- |
| 설계 | 1 | 구조·스토리라인·스타일 스펙 |
| 작성 | 장 수 | 스펙대로 장별 작성 (이미지는 저해상도 먼저) |
| 검증 | 1 | 장마다 스펙 대조 → 못 미치면 재생성. 렌더로 잰다 |

**금융 · 제조 같은 분석 도메인** — 자산 = 데이터·계산·결론. 판정 = 재계산·반증.

| 역할 | 수 | 하는 일 |
| --- | --- | --- |
| 수집 | 소스 종류 수 (공시·시세·내부 DB·현장 로그) | 소스 하나씩, 같은 반환 schema. 컷오프 뒤 사실은 조회로만 |
| 도메인 분석 | 1~2 | 계산·모델. 가정을 표로 명시 |
| 반증 | 1 | 주장마다 반대 근거·재계산. 살아남은 것만 넘긴다 |
| 종합 | 오케스트레이터 | 반증을 지난 것만으로 결론. 미검증은 미검증으로 |

리서치 일반은 `templates/recipes.md` §1(audit 형), 인프라 변경은 §2(migration 형)의 역할 배치를 그대로 쓴다.

## 2. 진행 단계별 관리 — 상태가 바뀔 때마다

| 단계 | 하는 일 | 기록 |
| --- | --- | --- |
| 착수 | 이번 작업에 뜨는 역할·각도 수·파일 소유·반환 schema 를 정한다 (`harness: limited|full · subagents: N · scope · return-schema · verify`) | 작업 카드 / TODO 항목 |
| 진행 중 | 새 각도가 보이면 ★역할 추가★. 한 역할이 두 일을 하고 있으면 ★분리★(전문성·병렬성·컨텍스트·재사용성 4축). 반대로 순차·가벼움·여기서만이면 ★합침★ | `.claude/agents/` 갱신 + README 표 |
| 병목 | 두 담당이 같은 파일을 기다리면 그 파일의 주인을 1명으로 옮긴다(공통부). 떼기 어려운 작은 교차 수정은 한 담당에게 같이 맡긴다 | README 소유권 표 |
| 검증 실패 | 고침은 ★원래 구현자 재호출★(출력 파일을 읽고 이어 간다). 검증자가 고치지 않는다 | 구현자 출력 파일 |
| 단계 전환 (예: 리서치 → 구현) | 도메인 표를 바꿔 다시 설계한다. 한 하네스에 두 도메인을 섞지 않는다 | README 갱신 |
| 종료 | 역할 정의는 남긴다(다음 작업이 재사용). 이번 작업 전용 역할만 지운다 | README 에 폐기 이유 한 줄 |

역할 변경은 ★파일부터★ 바꾼다. 프롬프트로만 바꾸면 다음 작업에서 옛 역할이 다시 뜬다.

## 3. 실사용 단계 — 신고·결정이 같은 시간에 계속 올 때 (모듈 × 역할)

팀장이 앱을 쓰면서 버그와 결정을 실시간으로 보내는 단계에서는 ★모듈 축 하나로는 부족하다★. 한 에이전트가 버그 재현과 새 디자인을 번갈아 하면 신고 처리가 늦고 보고가 뒤섞인다. 모듈 축 위에 ★역할 축★을 얹는다.

| 역할 | 받는 입력 | 루프 | 산출 |
| --- | --- | --- | --- |
| 🐞 버그 | 팀장 신고(원문 그대로) | ★재현 먼저★ → 원인 파일:줄 → 고침 → 같은 탐침 FAIL→PASS → 회귀 등록 | 커밋 + `{reproduced, cause, fixed}`. 재현 안 되면 `cannot_reproduce` + 잰 조합 + 팀장에게 조건 질문 ★1회★, 답 없으면 킵 |
| 🛠 구현 | 확정된 사양(PM 이 값을 정해 넘김) | 사양 정본 → 구현 → 단위 테스트 → 뮤턴트 → 사진 | 커밋 + `{done, not_done, needs, tests, mutants, shots}`. ★디자인은 사진(목업)을 먼저★ 팀장에게 보이고 확정 뒤 구현 |
| ✅ 검증 | 통합 sha(구현자와 다른 사람) | 사양 표에서 케이스 목록 → 구현자 탐침이 못 재는 행을 감사 탐침으로 보강 → 뮤턴트(모듈 섞어) → 사진 | `{items: pass|fail|cannot_measure, fail: [파일:줄+재현]}`. 제품 코드 무수정 |

PM(오케스트레이터)의 일: 신고 → 🐞 큐, 결정 → 🛠 큐, 둘을 ★같은 통합 브랜치★로 모아 ✅ 에 넘기고, 인수 게이트(전체 검사는 통합 sha 에서 ★한 번만★ — 병렬로 돌리면 3배 느려진다) → 공증/배포 → 팀장 보고. 예: 댓글 모듈의 🐞(⌘L·⌘↵·포커스)와 🛠(꼬리·답글 서랍)을 따로 띄운다.

지시는 ★한 번에 묶어★ 보낸다 — 에이전트에게 SendMessage 를 여러 번 나눠 보내면 순서가 어긋나 보정 사양이 빠진 채 끝난다(Steno 09-19: 줄번호 3상태·날짜 머리말·답글 서랍이 각각 한 번씩 빠졌다). 추가가 생기면 "남은 것 딱 N개" 로 한 메시지에 다시 묶는다.
