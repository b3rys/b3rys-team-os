# b3os-project-mgmt — 프로젝트 관리·보고

## 언제 작동?
- 팀장 요구가 ★여러 번 쌓이는 일★ — 앱·서비스·긴 기능. 단발 리서치·프로토는 대상 아님 (그건 `b3os-task-loop` 카드 하나로 충분).
- "목록으로 관리해" · "정리해서 보내봐" · "다 처리했어?" · "지금까지 나온 말로 정리하자".
- 킥오프 · 마일스톤 · 배포본 전달 · 다른 팀원에게 인계.

## 정본은 둘, 뷰는 여럿

| 무엇 | 정본 | 어디 |
|---|---|---|
| 팀장 지시·결함·킵 목록 | `TODO.md` | ★프로젝트 저장소 루트★ (git 동기화) |
| 과제 상태 (plan/doing/done) | 칸반 `task` 카드 | `team.db` (`b3os-task-loop`) |
| 채널 보고 | 위 둘에서 만든 ★뷰★ | 텔레그램·슬랙·팀버스 |

★같은 사실을 두 곳에 다른 값으로 적지 않는다.★ 보고문을 손으로 고쳐 쓰다 TODO.md 와 어긋나면 정본이 둘이 된다. 보고는 TODO.md 를 읽어 만든다.

## 목록 규율 — 팀장이 말한 것은 ★전부★ 들어간다

1. 팀장 메시지 하나 = 항목 하나 이상. 지시의 ★요지를 그대로★ 적고 시각(KST)·메시지 id·사진 경로를 단다. 요약만 남기면 나중에 "이게 무슨 얘기야" 가 된다. (TODO.md 는 프로젝트 저장소 안에 있으므로 그 저장소의 공개 여부에 따라 인용 수위를 맞춘다 — `b3os-github-workflow`.)
2. 상태는 셋 — `[ ]` 미착수 · `[~]` 진행중 · `[x]` 완료. 상태가 바뀌는 ★그 순간★ 갱신한다. 세션 끝에 몰아서 하지 않는다.
3. 팀장이 "킵" 이라 하면 `📌 킵` 섹션에 넣고 ★착수하지 않는다.★ 설계 논의가 나와도 착수 지시가 아니다.
4. 팀장이 방향을 바꾸면 옛 항목을 지우지 말고 ★"HH:MM 에 뒤집음"★ 을 달아 둔다. 같은 키가 하루에 세 번 뒤집히기도 한다.
5. 내가 찾은 결함도 같은 목록에 ★"<담당> 이 찾음"★ 표시로 넣는다. 팀장 것과 섞이면 누가 시켰는지 잃는다.
6. 내가 틀린 것은 ★저장소가 아니라 메모리(개인)·SHARED.md(팀 학습)에★ 적는다. 회고는 저장소에 남기지 않는다.

## TODO.md 모양 (프로젝트 저장소)

```markdown
# <프로젝트> — 작업 트래커
`[x]` 완료 · `[~]` 진행중 · `[ ]` 미착수

## 🎯 지향점 · 목표
## 🧱 정해진 구조 · 상시 기준
## 🔄 팀장 피드백 (YYYY-MM-DD HH:MM KST) — <담당> 관리      ← 팀장 메시지 묶음마다 하나
   - [ ] 항목 — 요지 · 사진 경로 · 원인(후보/확정) · 검증 기준
## 📌 킵 — 착수 안 함
## 🐛 별건 결함 — 검증 중 나온 것
## 🖐 팀장 손 검증 — 시험으로 못 재는 것
```

## 채널별 보고 포맷 — `references/channel-formats.md` 가 정본

| 채널 | 언제 | 모양 | 길이 |
|---|---|---|---|
| **텔레그램 1:1 · 정리** | "정리해서 보내봐" · 마일스톤 | 굵은 섹션 제목 + `·` 한 줄 항목 (아래) | 화면 한 번 스크롤 안 |
| **텔레그램 1:1 · 진행** | 진행 알림 · 질문 답 | ★두 줄★ — 무엇 → 어디 → 다음 | 2~5줄 |
| **슬랙** | 팀 공지·인수인계 | `b3os-slack-format` | 그 스킬대로 |
| **팀버스 (팀원)** | 위임·검토 결과 | `[태그] 한 줄 결론` + 근거 — CLAUDE.md 핵심룰(member↔member = function call) 그대로 | 인사·감사 없음 |
| **저장소 (커밋·PR)** | 병합 | `b3os-github-workflow` — 핵심 3~5줄 + 사실·인과만 | 회고·의견 없음 |

★텔레그램 정리 포맷★ — 섹션 제목만 굵게, 항목은 `·` 한 줄, 아이콘은 안 쓰거나 최소. 섹션마다 아이콘을 달면 "정신 없다" 는 답이 온다.

```
**<프로젝트> · M/D**

**지향** 한 줄
**목표**
1. … ← 지금
2. … (킵)
**구조** 한 줄로 · 로 잇기
**진행 중**
· …
**완료 (이번 주)**
· … · … · …
**킵**
· … · …
**손 검증** … · …
```

★텔레그램 진행 알림★ — 두 줄. 상세는 PR 본문·TODO.md 에 있으니 다시 적지 않는다.
```
<무엇> → <어디에 올림/들어감>, <다음>.
```

## 보고 규율

- 위임 뒤 대기는 `b3os-task-loop` 의 wait record(`recheck_at` · `fallback` · `escalation_after`)를 쓴다. 배달 성공은 일 시작이 아니다 — ★답장만이 신호★ 이고, 리듬을 넘기면 팀장에게 알린다.
- "다 처리했어?" 에는 ★숫자로★ 답한다 — "21건 중 19건". 남은 것과 막힌 이유를 같이.
- 내가 못 잰 것은 ★"못 쟀다"★ 라고 쓴다. 통과로 세지 않는다. 팀장 손 검증 목록으로 넘긴다.
- 배포본을 줄 때는 ★눌러볼 것★ 목록을 같이 준다 — 내가 못 잰 자리가 곧 팀장이 볼 자리다.

## 검증 규율

프로젝트 PR 검증은 `b3os-ai-code-safety` 를 따른다 (뮤턴트 · 양쪽 재기 · 화면은 사진에서 · 소스 진단은 재현 전까지 후보). 병합 메시지에는 ★잰 것 · 안 잰 것★ 을 적는다. 틀린 것은 메모리·SHARED.md 로.

## 인계 (다른 팀원에게 넘길 때) — 4줄
지시 요지 · 진행 여부 · 저장소·브랜치 기준점 · 범위. 하나라도 빠지면 받는 쪽이 멈추거나 엉뚱한 데서 일한다. 브랜치 기준점을 안 주면 앞 수정을 조용히 되돌린다.
