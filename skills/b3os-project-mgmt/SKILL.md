## 시간 규칙 — ★작업 상태로 움직이고, 시간은 크기 기준★

**진행은 시간 목표가 아니라 실제 작업 상태(끝남 · 막힘 · 남은 것)로 본다. 한 조각이 끝나면 바로 다음 과제를 시작한다.** 아래 시간 수치는 작업을 나누는 크기 기준이지 채워야 할 시간 칸이 아니다. 시간 칸에 묶여 끝날 때까지 기다리는 것이 가장 위험하다. 알린 창·슬롯보다 일이 일찍 끝나면 즉시 닫고 넘어간다.

**크기 기준 — 작업 단위 10분 + 병렬.** 모든 작업은 10분 이하 조각으로 나눠 병렬로 돌린다. 아래는 이 기준에서 나온다.

| 규칙 | 기준 |
|---|---|
| 순차로 잇지 않는다 | 단계를 이어 붙여 ETA 를 늘리지 않는다. 막히면 막힌 조각을 다시 쪼개 병렬로. 위임한 뒤 기다리지 않고 다음 조각을 한다 |
| 테스트·검증도 10분 단위 | 헤드리스는 병렬로, 앱·창 검사는 한 번 실행에 묶는다. 20분까지 가는 것은 ★예외★ — 잰 수치와 함께 알린다. 계획 예산으로 잡지 않는다 |
| 지시 → 전달본 | 30분 이하 |
| 품질은 깎지 않는다 | 시간은 방법(병렬·대기 제거)으로 줄인다. 검사를 빼서 줄이지 않는다 |
| ETA | 단계별 실측 시간의 합으로 낸다 |

## 목록 규율 — 팀장이 말한 것은 ★전부★ 들어간다

1. 팀장 메시지 하나 = 항목 하나 이상. 지시의 ★요지를 그대로★ 적고 시각(KST)·메시지 id·사진 경로를 단다. 요약만 남기면 나중에 "이게 무슨 얘기야" 가 된다. (TODO.md 는 프로젝트 저장소 안에 있으므로 그 저장소의 공개 여부에 따라 인용 수위를 맞춘다 — `b3os-github-workflow`.)
2. 상태는 셋 — `[ ]` 미착수 · `[~]` 진행중 · `[x]` 완료. 상태가 바뀌는 ★그 순간★ 갱신한다. 세션 끝에 몰아서 하지 않는다.
3. 팀장이 "킵" 이라 하면 `📌 킵` 섹션에 넣고 ★착수하지 않는다.★ 설계 논의가 나와도 착수 지시가 아니다.
4. 팀장이 방향을 바꾸면 옛 항목을 지우지 말고 ★"HH:MM 에 뒤집음"★ 을 달아 둔다.
5. 내가 찾은 결함도 같은 목록에 ★"<담당> 이 찾음"★ 표시로 넣는다. 팀장 것과 섞이면 누가 시켰는지 잃는다.
6. 내가 틀린 것은 ★저장소가 아니라 메모리(개인)·SHARED.md(팀 학습)에★ 적는다. 회고는 저장소에 남기지 않는다.

## 도메인별 에이전트 팀 — `references/agent-team-by-domain.md`

프로젝트를 열 때 에이전트 팀을 설계하고(만드는 역할 N · 판정하는 역할 · 통합하는 역할 + 공통부 주인 1명), 진행 단계마다 관리한다(각도가 늘면 역할 추가, 한 역할이 두 일을 하면 분리, 병목이면 주인 이동, 단계 전환이면 재설계). 실사용 단계(신고·결정이 실시간으로 올 때)는 모듈 축 위에 역할 축(🐞 버그·🛠 구현·✅ 검증)을 얹고 지시는 한 번에 묶는다(§3). 역할 정의는 프로젝트 저장소 `.claude/agents/` 에 파일로. 도메인 예시: 프로그램 개발 · 영상 · 콘텐츠 · 금융/제조 분석. 짜는 법의 정본은 `b3os-harness-playbook`.

## 보고 규율

- 위임 뒤 대기는 `b3os-task-loop` 의 wait record(`recheck_at` · `fallback` · `escalation_after`)를 쓴다. 배달 성공은 일 시작이 아니다 — ★답장만이 신호★ 이고, 리듬을 넘기면 팀장에게 알린다.
- "다 처리했어?" 에는 ★숫자로★ 답한다 — "21건 중 19건". 남은 것과 막힌 이유를 같이.
- 내가 못 잰 것은 ★"못 쟀다"★ 라고 쓴다. 통과로 세지 않는다. 팀장 손 검증 목록으로 넘긴다.
- 배포본을 줄 때는 ★눌러볼 것★ 목록을 같이 준다 — 내가 못 잰 자리가 곧 팀장이 볼 자리다.

## 검증 규율

프로젝트 PR 검증은 `b3os-ai-code-safety` 를 따른다 (뮤턴트 · 양쪽 재기 · 화면은 사진에서 · 소스 진단은 재현 전까지 후보). 증명 방법·래칫·검사가 틀렸을 때의 분류·한 번에 도는 러너는 `b3os-verification`. 병합 메시지에는 ★잰 것 · 안 잰 것★ 을 적는다. 틀린 것은 메모리·SHARED.md 로.

### 검증 사다리 — 어느 프로젝트든, 이 순서로

| 단계 | 무엇 | 통과 조건 |
|---|---|---|
| ① 기준 먼저 | 코딩 전에 잴 것을 정한다. **사용자 행동 스크립트**("이렇게 하면 → 이렇게 된다" 행) + **상태 × 사건 표**(항목에 붙는 모든 상태 × 수명 사건: 전환·닫기·종료·삭제·복원·이름 바꿈·이동·재실행·외부 변경 …) | 새 기능은 행부터 추가한다. 빈 칸 = 미검증 |
| ② 헤드리스 | 단위 + 통합 + 무작위 리그 | 칸마다 테스트 + 그 테스트가 잡는 뮤턴트(일부러 깬 코드) 기록이 있어야 입증. "후보" 칸은 입증으로 세지 않는다 |
| ②′ 최신성 가드 | 코드↔표: 코드에 있는데 표에 없는 상태 = 실패, 없는 코드를 가리키는 행 = 실패. 스크립트↔감사표 1:1: 감사 행 없는 스크립트 행 = 실패 | 실패하면 먼저 "제품인가, 검사인가" 를 가른다(`b3os-verification` §5) |
| ③ 리뷰 | 작성자 아닌 사람이 본다 | 턴 크기 변경 = 리뷰어 1명 |
| ④ 통합 | 통합 브랜치에 머지할 때마다 전체 스위트 | 전부 통과 |
| ⑤ 릴리스 검사 | 명령 하나가 빌드·서명, 헤드리스 인수, 앱 검사 묶음, 속도 게이트를 겹쳐 돌린다. 검사기 자체 테스트 포함(`b3os-verification` §7) | sha 하나가 전부 통과. 속도 회귀 = 릴리스 금지 |
| ⑥ 전달 | 산출물 자체를 검증(예: 공증) | 사람만 확인할 수 있는 것 목록을 같이 준다(위 "보고 규율") |

뮤턴트 거는 법은 `b3os-ai-code-safety` Phase 4 · `b3os-verification` §4. 실물 예: 첫 적용 프로젝트의 `docs/acceptance/`(예: `verification-process.md` 한 장) — 각 프로젝트도 같은 자리에 둔다.

**측정 위생**
- 시간 측정은 선언한 조용한 구간에서 한다 — 팀원 ack 를 받고, 측정 중 부하를 기록한다.
- A/B 는 회차를 번갈아 돈다. 분포가 겹치면 결과는 PASS 가 아니라 ★판정 불가★.
- 앱 탐침은 띄운 바이너리 경로가 요청한 빌드인지 확인한다 — 번들 id 가 같은 사본을 OS 가 대신 띄울 수 있다.
