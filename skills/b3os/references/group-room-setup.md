# 팀방(그룹) 협업 셋업 — System OP 봇

> **이름 정리** — 이 봇은 문서·UI 곳곳에서 **System OP 봇 = 팀 라우터 = capture 봇**으로 불린다(같은 하나). 대시보드 라벨은 **"시스템 OP"**, 토큰 입력칸은 **"capture 봇 토큰"**. 아래는 전부 이 한 봇 얘기다.

첫 팀원은 **1:1 DM**으로 충분하다(그룹·System OP 봇 불필요). 하지만 **여러 팀원을 한 텔레그램 그룹에 모아
함께 대화**하고 싶으면 **System OP 봇**을 붙인다 — 이 봇이 팀 텔레그램 **그룹의 입구(ingress, 수신 경로)**
역할을 해서 그룹 메시지를 담당 팀원(에이전트)에게 라우팅한다. 즉 System OP 봇은 **그룹 협업을 켜는
스위치**이지 모니터링 알림 봇이 아니다.

## 언제 필요한가 / 안 해도 되는 것 (헷갈리기 쉬움 — 정확히)

- **필요한 경우**: ①팀 텔레그램 **그룹방에서 여러 팀원이 자동으로** 대화에 끼어들게 하고 싶을 때 ②`/status`·`/board`·`/digest`·`/approve` 같은 **팀 운영 명령/알림**을 텔레그램으로 쓰고 싶을 때.
- **필요 없는 경우 (router OFF / System OP 미설정이어도 그대로 동작)**: ①**1:1 DM** — 각 팀원 자기 봇에 직접 말 걸기 ②**팀원끼리 협업(handoff·버스)** — 한 팀원이 다른 팀원에게 위임·요청하는 것. 이 둘은 System OP·라우터와 **무관하게 동작한다**(라우터는 오직 '그룹방 자동응답'만 켜고 끈다).

그래서 팀방을 안 만들어도 팀은 돌아간다 — System OP 는 "그룹방 자동협업 + 운영 알림"을 원할 때만 붙이는 **선택** 레이어다.

## System OP 봇이 하는 일 (정확히)

- **그룹 ingress** — 팀 텔레그램 그룹을 읽어 각 메시지를 담당 팀원에게 라우팅.
- **온디맨드(on-demand) 명령** — 그룹/DM에서 물으면 그때 답하는 명령: `/status`(팀 상태) ·
  `/board`(칸반) · `/digest`(요약) · `/approve`(민감 실행 승인) · `/onoff`(라우터/기능 토글).

> ⚠️ **System OP 봇은 "시스템 오퍼레이터"입니다 — 대화모드 OFF.** 팀원처럼 잡담·대화하지 않습니다.
> 그룹을 연결(ingress/라우팅)하고 **명령**(`/status` `/board` `/digest` `/approve` `/onoff`)에만 답할 뿐입니다.
> 그러니 사용자에게 이 봇을 **팀원처럼 "말 걸 수 있는" 대상으로 안내하지 마세요** — 대화는 팀원(에이전트)에게, OP 봇은 명령에.

## 셋업

사람이 할 일은 셋이다 — 봇 1개 + 그룹 chat_id + op 봇을 그룹 관리자로. 각 단계에 "왜 / 흔한 실패 / 확인법"을 붙였다.

1. **op 봇 생성** — BotFather로 **System OP 전용 봇**을 하나 더 만들어 토큰을 받는다(팀원 봇과 **별개**의 봇). *(왜: op 봇은 팀원이 아니라 그룹 입구·운영 명령 전용. · 확인: `/newbot` 이 준 토큰을 받으면 됨 — 토큰 값은 화면·로그에 다시 노출하지 않는다.)*

2. **그룹 생성 + 봇 초대 (★op 봇은 관리자로★)** — 팀원들을 넣을 **텔레그램 그룹**을 만들고 **op 봇 + 각 팀원 봇**을 초대하되, **op 봇은 관리자(admin)로 추가**한다(3번 이유). 팀원 봇은 일반 멤버로 충분하다 — 그룹 대화를 읽는 건 op 봇 하나다. *(확인: 그룹 멤버 목록에 op 봇이 관리자로, 팀원 봇이 멤버로 보이면 됨.)*

3. **★op 봇을 그룹 관리자(admin)로 올리기 — 가장 자주 빠뜨리는 단계, 안 하면 라우팅이 통째로 안 된다★** — 그룹 설정 ▸ 관리자 ▸ op 봇을 관리자로 추가. 2번에서 초대할 때 바로 관리자로 넣으면 이 단계를 따로 안 밟아도 된다.
   - **왜**: 텔레그램 봇은 기본적으로 그룹에서 **자기에게 온 명령(`/cmd`)·자기 멘션·자기 답장만** 받고 **일반 그룹 메시지는 못 받는다**(privacy mode, BotFather 기본값 = Enabled). 그러면 capture 봇이 그룹 대화를 못 읽어 라우팅(멘션 없는 지시·다른 팀원 멘션)이 전혀 동작하지 않는다. **관리자는 이 제한을 받지 않아** 전체 메시지를 받는다.
   - **대안**: @BotFather → `/setprivacy` → op 봇 선택 → **Disable** 로도 같은 효과를 낸다. 관리자로 못 올리는 그룹이거나 BotFather 설정을 선호할 때 쓴다.
   - **흔한 실패**: 이 단계를 건너뛰면 아래 4-b 자동감지가 `no_group_seen` 으로 그룹을 못 찾고, 라우터를 켜도 그룹에서 아무도 응답하지 않는다.
   - **확인**: 4-b 자동감지가 그룹을 찾아내면 = 캡처가 실제로 되고 있다는 증거.

4. **대시보드 Settings ▸ 시스템 OP (System OP)** 에서 —
   - **(4-a) capture 봇 토큰 입력** → **봇 연결 확인** 버튼을 누르면 봇 username 이 떠서 토큰 유효성이 검증된다(내부: `POST /system-op/check` = 텔레그램 `getMe`). *(적용 시점: 대시보드가 저장 후 "즉시 적용" 또는 "재시작 시 적용"을 표시해준다 — 표시대로 따른다.)*
   - **(4-b) 그룹 chat_id 설정 (자동감지 권장)** — op 봇이 그룹에 든 상태에서 그룹에 **아무 메시지나 하나** 올린 뒤, **Claude Code에게 "우리 그룹 chat_id 알려줘"** 라고 하면 자동으로 찾아 설정한다(내부: `POST /system-op/detect-group` — capture 워커가 이미 본 그룹을 조회하고, **그룹이 하나면 자동 지정**·둘 이상이면 목록을 주고 고르게 한다). `no_group_seen` 이 뜨면 → op 봇이 그룹에 있는지 + **3번 op 봇이 그룹 관리자인지**(또는 privacy Disable) + 그룹에 메시지를 하나 보냈는지 확인 후 재시도. 수동으로 넣어도 된다 — 그룹에 잠깐 **@userinfobot**(또는 @RawDataBot)을 초대하면 chat_id(대개 `-100…`)를 알려준다.
   - **(4-c) Router ON** (시스템 OP 토글 또는 `.env` `ROUTER_ENABLED=true`). ★라우터 토글은 즉시 반영★(재시작 불필요).

5. **동작 확인** — 그룹에 `@팀원` 멘션 또는 `/status` → 응답이 오면 팀방 협업 준비 완료. 응답이 없으면: ①라우터가 ON 인지 ②op 봇이 그룹 관리자인지(3번, 또는 privacy Disable) ③그룹 chat_id 가 맞게 잡혔는지 순으로 본다.

## 헬스 모니터링은 대시보드에서만 본다 (정직하게)

- b3os는 에이전트 위험/복구 감지·라이브 상태 같은 **헬스 모니터링을 자동으로** 돌리지만, 그 결과는
  **대시보드(Topology/Team 탭)에서만** 보인다. **b3os는 텔레그램으로 헬스 알림을 push 하지 않는다.**
- 공개 빌드에는 **auto-heal(자동복구)도, 예약 digest 자동 푸시도 없다** — 그건 별도 내부 전용
  스크립트/launchd이고 **공개 저장소에서 제외**돼 있다. (`/digest` 명령은 물었을 때 답하는 온디맨드일 뿐,
  주기적으로 알아서 보내주지 않는다.)
- 그러니 **"뭔가 깨지면 텔레그램으로 알려준다"고 안내하지 말 것** — 공개 빌드에선 사실이 아니다. 상태는
  **대시보드에서 확인**하고, System OP 봇은 **ingress + 온디맨드 명령**만 한다고 정직하게 안내한다.
