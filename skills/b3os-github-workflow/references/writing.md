# 저장소에 남는 글 — 사실과 인과만

## 무엇을 쓰나 — 저장소에 남는 글은 사실과 인과만

저장소에 들어가는 것은 전부 공개물이다. 용도가 정해져 있다.

| 어디 | 무엇을 |
|---|---|
| README·가이드 | 하는 방법 + 확인 방법 |
| PR 본문 | 무엇이 문제인가(사실) → 왜 그렇게 되나(인과) → 어떻게 고쳤나 → 검증 결과 |
| 커밋 메시지 | 무엇을 바꿨고 왜 그게 맞는가 |
| 코드 주석 | 이 코드가 무엇을 하는가, 왜 이 조건이 필요한가 |
| **메모리·SHARED.md** | **회고·리뷰는 전부 여기.** 밖에 안 나간다 |

**빼는 것은 회고성 서술이다** — 사고 경위, "오늘 우리가", 작업 과정의 날짜, 그 일에 관계없는 사람 이름.

절차가 요구하는 신원은 그대로 쓴다 — 커밋 author, PR 본문의 `Submitted-by`, 코드에서 참조하는 버전·날짜.

### 같은 내용을 두 가지로 쓰면

```
안 쓴다:
  "왜 아무도 못 봤나 — 테스트가 실제 서버가 만들 수 없는 요청을 쓴다.
   3회전 검증도 못 봤고, 403 을 여러 번 보고도 정상으로 읽었다."

쓴다:
  "판정의 두 조건이 배타적이다. Bun 은 request.url 의 authority 를 Host 헤더로
   만들므로 도메인 요청에서는 isLoopbackHost(urlHost) 가 항상 거짓이다.
   앞 조건의 역할은 TEAM_BIND 루프백 검사가 대신한다. 그래서 제거했다."
```

같은 내용인데 짧고, 읽는 사람이 판단할 수 있다.

### 가이드 문서에서 특히

버전 이력 대신 **확인 방법**을 준다.

```
안 쓴다:  "이 설정은 <날짜> 까지 동작하지 않았다."
쓴다:    "설정하고 서버를 다시 띄운 뒤 그 주소로 열어 보세요.
          안내 페이지가 그대로면 아직 적용되지 않은 것입니다."
```

경고는 사례 없이 **규칙만으로** 쓴다. 그게 더 세다.

```
안 쓴다:  "<날짜> 에 로그인 관문 없이 열려 있던 주소가 있었고…"
쓴다:    "등록하면 그 주소로 들어온 사람은 누구든 팀리드가 됩니다.
          내부망이거나 앞에 로그인 관문이 있는 주소만 등록하세요."
```

### 판별 질문

> **이 문장이 없으면 읽는 사람이 못 하거나, 판단·검증할 수 없는 것이 있나?**

없으면 회고다. 빼고 메모리에 쓴다. 길면 그 자체로 회고가 섞인 것이다.

검증 근거와 미검증 범위는 **판단에 필요하므로 남긴다** — 독자가 직접 실행하지 않아도 그렇다.
