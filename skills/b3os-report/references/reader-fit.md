# 독자 중심 보고서 점검

보고서를 쓰기 전과 내용 리뷰 때 사용한다. 문체·SVG 구현은 기존 스킬을 따르고, 여기서는 **무엇을 어느 순서로 배울지**를 점검한다.

## 1. 첫 질문과 하나의 예

- 독자가 이 보고서로 답하려는 질문을 한 문장으로 정한다. 원자료의 목차를 그대로 옮기는 것이 기본은 아니다. 원문 순서가 요청됐다면 유지하되 기초 읽기 경로를 먼저 제공한다.
- 하나의 실제 상황 또는 명시된 설명용 예를 고르고, 같은 대상을 주요 절과 그림에서 이어간다. 비교에서 고정한 입력·단위·판정 기준과 바꾼 것을 명시한다. 목적이 달라 기준을 바꾸면 이유를 설명한다.
- 첫 흐름은 입력 → 무엇을 바꾸는지 → 결과 → 결과의 의미까지 끝낸다. 그 전에 학습법 역사나 모델 목록으로 우회하지 않는다.
- 한 절이 끝나면 새로 알게 된 사실이 다음 절에서 왜 필요한지 연결한다. 이름을 정의했어도 당장 쓰이지 않으면 뒤로 보낸다.

## 2. 기본 본문과 선택형 심화

기본 본문에는 질문의 답과 판단을 바꾸는 조건을 남긴다. 수식 유도·전체 설치 코드·내부 구현·지표 목록·재현 절차는 필요할 때 펼칠 심화/부록으로 분리한다. 사용자가 계산이나 코드를 물었다면 그것이 본문이다. 무조건 빼지 않는다.

- 제품 설명이라면 무엇을 받아 무엇을 돌려주는지 먼저 보여준다. 설치 명령보다 사용 장면을 먼저 이해하게 한다.
- 계산 설명이라면 쉬운 사칙연산으로 한 번 끝까지 계산한다. 바꾼 값과 그대로 둔 값을 함께 표시한다.
- 한계를 모두 끝으로 몰지 않는다. 설명용 수치인지, 실제 측정인지, 적용 조건이 무엇인지는 관련 결과 바로 옆에 둔다. 같은 주의 문장을 모든 문단에서 반복하지 않는다.
- 초보자에게 필요한 기준과 심화 지표를 구분한다. 기본 지표 하나를 이해하기 전에 여러 지표의 정의를 나열하지 않는다.

## 3. 용어와 그림

낯선 모델·제품·약어는 ‘무엇이고, 지금 예에서 무슨 일을 하는지’로 설명한다. 영문 풀네임이나 종류명만으로 끝내지 않는다. 약어가 아닌 제품명의 풀네임을 만들지 않는다.

설명그림은 `diagrams.md`에 따라 만들되, 다음을 점검한다.

- 같은 예의 입력·처리·결과, 또는 바꾸기 전후가 보이는가?
- 그림을 읽는 데 아직 설명하지 않은 전문용어가 필요한가?
- 그림 아래 한 문장으로 무엇이 달라졌고 왜 중요한지 말할 수 있는가?
- 그림 수를 채우려고 새 개념을 추가하지 않았는가? 설명용 수치는 실제 성능과 구분했는가?

## 4. 리뷰: 개수 대신 재설명

리뷰어는 기본 본문만 읽고 다음을 자기 말로 짧게 써 본다.

1. 이 기술·주제는 어떤 문제를 다루나?
2. 같은 예에서 무엇을 입력하고, 무엇을 어떻게 바꿔, 어떤 결과를 얻나?
3. 왜 도움이 되며, 그 결과로 아직 말할 수 없는 것은 무엇인가?

답을 쓰기 위해 부록의 용어 풀이를 오가야 하거나, 앞에서 배우지 않은 개념을 새로 설명해야 하면 그 구간을 수정한다. 막힌 구절·빠진 연결·앞당기거나 뒤로 보낼 내용을 특정한다. ‘쉽게/짧게 써라’만으로 반려하지 않는다.

이 검사는 독립 독자 관점의 대리 검토이지 실제 사용자 이해의 증명은 아니다. 사용자가 어렵다고 한 경우 검토 통과를 근거로 반박하지 말고, 어느 연결에서 막혔는지 반영한다.
