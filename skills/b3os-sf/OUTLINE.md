# b3os SF 공개 문서 뼈대

이 문서는 특정 운영체제나 제품에 묶이지 않는 소프트웨어 구축·출시·운영 방법론의 목차다. 각 절은 이후 본문을 채울 때 다룰 범위와 경계를 먼저 고정한다.

## 한 장 순환 그림

```text
[START] -> [BUILD] -> [RELEASE] -> [OPERATE]
    ^          |           |           |
    |          v           v           v
    +------ [KNOWLEDGE] <---+-----------+
                 |
                 v
       [CHALLENGE -> ADOPT]
                 |
                 +----> [RECHECK]
```

요구와 설계에서 시작한 작업은 개발·출시·운영을 거치며 근거를 만든다. 근거는 지식으로 쌓고, 반대 의견과 재확인을 거쳐 다음 시작과 개발의 입력으로 되돌린다.

## 1. 시작

요구 원문을 보존한 첫 기능 목록을 만들고 확인받는다. 바꾸기 비싼 결정만 초기 설계에 담는다: 시스템 구성도, 핵심 클래스·모듈, 데이터베이스와 데이터 흐름, 보안 경계다.

설계를 확인받은 뒤 저장소, 문서, 지속적 통합(CI), 첫 실행 경로가 있는 최소 뼈대를 만든다. 아직 쓰지 않는 기능을 위한 구조는 미리 만들지 않는다.

## 2. 개발

모든 변경은 `요청 -> 만들기 -> 검사 -> 리뷰 -> 머지 승인 -> 내보내기 -> 보고 -> 배우기` 순환으로 관리한다. 기본 작업 단위는 10분이며, 각 단위는 확인 가능한 산출물이나 다음 판단을 남긴다.

시험은 사용자 시나리오 자동 스크립트와 실제 버그의 회귀 시험을 기본으로 한다. 가능한 조합을 모두 나열하는 전수 표는 데이터 유실과 보안처럼 실패 비용이 큰 영역에만 쓴다.

## 3. 출시

개발·시험·사용자 전달 단계를 분리할 수 있도록 `dev`, `beta`, `release` 채널을 정의한다. 각 채널의 진입 조건, 승격 조건, 되돌리는 방법을 기록한다.

자동 업데이트와 배포 산출물의 무결성을 다루고, 플랫폼이 요구하는 서명·공증 절차는 플랫폼별 확장 문서로 연결한다. 출시 게이트를 넘기는 예외에는 사람 승인이 필요하다.

## 4. 운영

가용성·성능·오류를 감시하고, 장애 때는 영향 제한과 복구를 먼저 한 뒤 원인 제거를 개발 순환으로 돌려보낸다. 버그와 크래시도 수집, 재현, 수정, 회귀 시험, 배포, 실사용 확인의 자동화 가능한 루프로 다룬다.

되돌리기 어려운 변경, 데이터·보안 영향, 출시 게이트 예외에는 사람 승인을 둔다. 정기 정비와 사용자 피드백은 새 요청으로 기록해 같은 개발 순환에 넣는다.

## 5. 지식

노하우는 세 곳에 쌓는다: 프로젝트 저장소의 프로젝트별 근거, 플랫폼 스킬의 재사용 가능한 지식, 주간 러닝 세션의 공통 학습이다. 예를 들어 macOS 앱의 플랫폼 지식은 `apple-app-shell`에 두고 방법론 본문과 분리한다.

RSI 순환은 지식을 쌓고, 반대 의견으로 검토하고, 채택 범위·조건·재확인 시점을 기록하는 과정이다. 재확인 결과는 기존 지식을 유지·수정·폐기하는 근거가 된다.

## 6. 프로젝트 문서 틀

`README.md`는 새 참여자가 목적, 현재 상태, 시작 방법, 문서 지도를 찾는 입구다. 요구·기능·설계·작업·검증 문서는 각각의 정본을 하나만 두고 README에서 연결한다.

운영 개요는 시스템 구조, 데이터와 설정, 역할, 작업 흐름, 출시, 외부 연결, 안전 규칙, 문서 지도를 한 장에 모은다. 세부 절차는 별도 문서로 연결하며 현재 상태와 계획을 섞지 않는다.

## 7. 체크리스트

시작·개발·출시·운영·지식 단계별 필수 입력, 산출물, 확인 지점, 사람 승인 지점을 점검한다. 확인하지 않은 항목은 통과가 아니라 미검증으로 표시한다.

프로젝트 시작 체크리스트와 반복 변경 체크리스트를 나누고, 각 항목은 저장소 파일·시험 결과·배포 기록처럼 재현 가능한 근거를 가리키게 한다.

## 8. 사례

Steno와 b3chat 사례는 방법론의 각 단계가 실제 프로젝트에서 어떤 산출물로 나타났는지 보여준다. 저장소에서 확인되는 파일, 검사 결과, 소요 시간 등 실제 숫자만 사용한다.

사례는 성공담이 아니라 조건·선택·결과·한계를 비교하는 형식으로 쓴다. 확인할 수 없는 수치와 팀 대화는 포함하지 않는다.

## 9. 부록

b3os 전용 도구, 명령, 내부 경로, 채널별 보고 형식은 본문에서 분리해 부록에 둔다. 본문은 다른 팀과 도구에서도 적용할 수 있는 원칙과 완료 조건에 집중한다.

플랫폼별 서명·공증, 자동 업데이트, 패키징 절차도 확장 부록이나 별도 플랫폼 스킬로 연결한다. 환경별 예시는 방법론의 필수 조건으로 표현하지 않는다.
