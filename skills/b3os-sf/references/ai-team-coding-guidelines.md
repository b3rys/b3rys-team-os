# AI 팀 코딩 지침

이 지침은 특정 앱이나 플랫폼에 묶이지 않는다. 각 원칙은 기능을 만들 때 바로 확인할 수 있는 행동으로 쓴다.

용어를 먼저 푼다.

- **토큰량:** AI가 읽고 쓰는 텍스트를 세는 단위의 양.
- **자기 타입:** 한 기능의 데이터와 동작을 맡는 전용 코드 구조.
- **언어 표:** 같은 화면 문구를 지원 언어별로 모아 둔 파일.
- **비동기:** 오래 걸리는 일을 화면을 멈추지 않고 따로 실행하는 방식.
- **리터럴:** 설정 파일이나 언어 표가 아니라 코드에 직접 쓴 숫자·경로·문구.
- **입구:** 같은 값을 바꾸거나 읽는 코드가 지나가는 자리(함수·모듈 하나).
- **디자인 토큰:** 색·글자 크기·간격·모서리·투명도·그림자 같은 화면 디자인 값을 이름 붙여 모아 둔 데이터. 테마는 같은 토큰 이름에 다른 값을 넣은 묶음이다.

## 1. 새 기능은 자기 타입과 자기 설정 파일에 둔다

- **원칙:** 새 기능을 공용 클래스에 조건문으로 붙이지 않는다.
- **왜:** 공용 클래스에 기능 조건문이 쌓이면 한 기능을 고칠 때마다 다른 기능이 깨진다. 예: 새 실행 도구는 도구 타입과 도구 설정 파일을 만들고 공용 화면에는 목록만 전달한다.
- **적용 사례:** 보기 화면의 줄 색을 편집기 공용 설정에 합쳐 편집기 코드를 건드렸다. 이를 되돌리고 보기 화면이 자기 설정값을 따로 쓰게 했다.
- **어떻게:** 변경 파일 목록에서 새 기능 전용 타입·설정 파일이 있는지, 공용 클래스에 기능 이름 조건문이 늘지 않았는지 확인한다. 완료 기준에 "기존 경로 무변경"을 적고 리뷰 첫 질문은 "잘되던 기능의 파일이 diff 에 있나"로 한다. 같은 값이 필요하면 기존 쪽을 고치지 않고 복제해 따로 둔다. 공통 코드를 꼭 바꿔야 하면 아키 리뷰로 필요성·범위를 판단하고 그 공통 코드를 쓰는 기능 검사까지 돌린다.

## 2. 구조화해 고친 곳만 검사한다

- **원칙:** 기능 경계를 나누면 고친 모듈 검사로도 품질을 지킬 수 있다.
- **왜:** 영향 범위가 좁으면 고친 곳만 검사해도 품질이 지켜진다. 사례는 [`dev-mode-operations.md`](dev-mode-operations.md#관측된-속도와-하한)의 적용 사례.
- **어떻게:** 기능을 일부러 고장 낸 코드로 테스트가 잡는지 확인한다. 이 코드를 뮤턴트라고 한다.

## 3. 변경 파일로 검사 4단계를 자동 선택한다

- **원칙:** 검사를 사람이 기억해서 고르지 않고 변경 파일 표가 고른다.
- **왜:** 검사를 사람이 기억해서 고르면 빠뜨리거나 매번 전체를 돌린다. 예: 문서 파일만 바꿨다면 문서 링크 검사부터 돌리고, 전체 제품 검사는 출고 단계에서 돌린다.
- **어떻게:** [`dev-mode-operations.md`의 검사 4단계와 선택 방법](dev-mode-operations.md#변경-파일로-자동-선택하는-검사-4단계)을 따른다.

## 4. 리팩터링은 목표가 아니라 신호에 대한 대응이다

- **원칙:** 개발 모드의 검사표에서는 기능 하나 때문에 검사가 3단계까지 올라갈 때만 구조 변경을 제안한다.
- **왜:** 기능 하나가 연관 기능 검사까지 부르면 경계가 섞인 것이다. 예: 작은 기능이 공용 파일을 건드려 연관 기능 검사까지 요구한다.
- **어떻게:** 검사 표가 3단계를 고른 이유를 기록하고, 기능 전용 타입·설정으로 분리할 수 있는지 검토한다. 수정 집중·테스트 교차 실패 같은 일반 구조 신호는 [`development.md`](development.md#구조-가드)를 따른다.

## 5. 기능 머지마다 짧게 구조를 검토한다

- **원칙:** 기능을 합치기 전에 자리·분기·중복만 짧게 본다.
- **왜:** 구조 결함은 합치기 전에 잡는 비용이 가장 싸다. 예: 새 기능의 조건문이 공용 진입점 세 곳에 생겼다면 합치기 전에 입구를 하나로 모은다.
- **어떻게:** PR에 “제자리인가, 새 분기가 생겼나, 같은 값의 입구가 둘 이상인가” 세 질문의 답을 남긴다.

## 6. 화면 문구는 언어 표에서 관리한다

- **원칙:** 사용자에게 보이는 문구를 코드에 직접 쓰지 않는다.
- **왜:** 문구가 코드에 흩어지면 언어를 추가하거나 문구를 고칠 때마다 코드를 고친다. 예: 버튼 문구를 언어 표에 두면 한국어·영어 누락을 한 검사에서 잡는다.
- **적용 사례:** 한 앱은 이 규칙이 있었지만 첫날 검사가 없어 화면 문구 리터럴이 약 375곳 쌓였다.
- **어떻게:** 소스의 화면 문구 리터럴을 금지하는 검사와 언어 표의 모든 지원 언어 칸 검사를 머지 조건으로 둔다. 검사·스크립트도 화면 문자열을 직접 쓰지 않고 언어 표 값으로 비교하며, 화면 이름을 바꿀 때는 소스·테스트·스크립트 전체를 grep 해 완료 기준에 넣는다. 지원 언어가 둘 이상이면 새 기능의 완료 기준과 출시 검사에 각 언어 화면 확인을 넣는다.

## 6-1. 화면 디자인 값은 디자인 토큰에서 읽는다

- **원칙:** 색·글자 크기·간격·모서리·투명도·그림자를 화면 코드에 직접 쓰지 않는다. 화면은 토큰 이름으로만 값을 읽고, 값은 테마 데이터 한 곳에 둔다. 테마를 바꾸는 기능이 없어도 같다.
- **왜:** 디자인 값이 화면 코드에 흩어지면 테마를 바꿀 때 화면 파일을 하나씩 뒤져야 한다.
- **적용 사례:** 한 앱은 색 역할을 테마 파일에 모았지만 강조색이 코드 상수였고, 반응 아이콘 색 22개와 그림자·투명도 숫자 57곳이 화면 코드에 박혀 있었다. 라이트 모드 색을 고치려면 화면 파일을 하나씩 뒤져야 했다.
- **어떻게:** 프로젝트 첫날 토큰 파일과 읽는 코드를 만들고, 화면 소스의 색 리터럴(hex·RGB 생성자·이름 붙은 기본색)·숫자 투명도·고정 크기를 찾는 검사를 머지 조건으로 둔다. 이미 쌓인 프로젝트는 현재 개수를 기준값으로 적고 늘면 실패하게(래칫) 한 뒤 줄여 간다. 6번 언어 표 검사도 같은 방식으로 함께 건다.

## 7. 설정값은 코드가 아니라 설정 파일에 둔다

- **원칙:** 시간·크기·경로·기능 켜짐 같은 운영값을 코드에 박지 않는다.
- **왜:** 운영값이 코드에 박히면 환경별 조정과 문구 수정이 코드 변경·빌드·검증이 된다. 예: 검사 제한 시간을 설정 파일에 두면 환경별 값을 코드 변경 없이 조정한다.
- **어떻게:** 새 숫자·경로·문구가 코드에 생기면 설정 파일에 둘 값인지 검토하고(AI 지시문 포함, 코드에는 불변식·프로토콜 상수만 남긴다), 위임할 때 "상수 박지 말 것"을 명시하고 과제 완료 기준에 "문구·숫자=설정 파일"을 적고 가드 테스트로 막는다. 코드에 박힌 것을 고칠 일이 생기면 고치는 김에 옮긴다. 개발·테스트·출시 환경 값을 분리한다.

## 8. 사이드 이펙트는 조건문이 아니라 구조로 막는다

- **원칙:** 한 기능 수정이 다른 기능을 깨뜨리면 예외 조건을 덧대지 말고 경계를 나눈다.
- **왜:** 특정 경로에 예외 조건을 덧대면 그 경로만 막히고 같은 원인은 다른 경로로 다시 터진다. 예: 화면을 그리는 중 상태를 바꾸지 않고, 탐색은 비동기로 실행한 뒤 결과만 화면에 전달한다.
- **어떻게:** 한 구역을 일부러 고장 냈을 때 다른 구역 테스트가 깨지는지 확인하고, 깨지면 상태·입구·설정의 소유자를 분리한다. 사이드이펙트 버그의 위임·보고에는 ① 꼬인 상태가 무엇·어디·누구 소유인지 ② 구조가 왜 허용했나 ③ 구조적 고침(값 주인 하나·모든 전환이 한 곳 통과·캐시 대신 파생, 경로별 if 금지) ④ 종류 전체를 잡는 불변식 검사 ⑤ 설계 문서의 규칙을 요구한다. 30분을 넘기면 가장 작은 구조적 한 걸음부터 한다.

## 9. 여러 곳이 같이 쓰는 값은 쓰는 입구를 하나로 둔다

- **원칙:** 오류 알림 칸·현재 선택 항목처럼 여러 기능이 같이 쓰는 값은 기능마다 직접 바꾸지 않는다. 각 기능은 "이렇게 바꿔 달라"고 입구 하나에 부탁하고, 실제로 값을 쓰는 곳은 그 입구 하나다.
- **왜:** 같은 값을 여러 곳이 직접 바꾸면 덮어쓰기 규칙·순서·기록을 한 곳에서 정하고 테스트할 수 없다.
- **적용 사례:** 한 앱에서 창 위 오류 알림 한 칸에 기능 9개가 직접 썼다. 두 일이 거의 동시에 실패하면 나중 문구가 앞 문구를 덮어 저장 실패 같은 중요한 알림이 사라질 수 있었다. 지금 고른 노트도 15곳이 직접 바꿔 원인 찾기가 어려웠다. 입구를 하나로 모으자 덮어쓰기 규칙·순서·기록을 한 곳에서 테스트할 수 있게 됐다.
- **어떻게:** 값마다 쓰는 곳을 세어 표로 고정하고(늘면 실패하는 검사), 입구를 건너뛰는 직접 쓰기 하나를 일부러 되살렸을 때 검사가 실패하는지 확인한다. 바꾸는 동안 동작은 그대로 두고 기존 테스트는 고치지 않는다.

## 10. 한 클래스가 아니라 앱 전체 구조에서 잰다

- **원칙:** 큰 클래스를 정리할 때 그 클래스 안만 보지 않는다. 먼저 앱 전체의 층(화면·로직·상태·외부 연결)과 의존 방향을 그리고, 그 지도에서 그 클래스가 맡을 일을 정한다.
- **왜:** 한 클래스 안만 재면 같은 값을 밖에서 바꾸는 곳을 놓친다.
- **적용 사례:** 한 앱에서 공용 상태 클래스 안의 "지금 고른 노트" 변경 15곳을 입구 하나로 모았지만, 클래스 밖 화면 코드 7개 파일에 같은 값을 직접 바꾸는 곳이 13곳 더 있었다.
- **어떻게:** 정리 대상 값·함수마다 저장소 전체에서 쓰는 곳을 센다(테스트용 코드는 따로 표시). 숫자를 "클래스 안 / 밖"으로 나눠 적고, 밖에서 쓰는 곳이 있으면 그 화면 코드가 어느 층에 있는지부터 정한다.

## 11. 테스트는 소스 글자가 아니라 기능을 밖에서 확인한다

- **원칙:** "이 파일에 이 코드 줄이 있어야 한다"처럼 소스 글자를 읽어 확인하는 테스트는 만들지 않는다. 기능을 밖에서 불러 결과(파일·저장된 글·화면 상태)를 확인한다. "화면 코드에 문구 직접 쓰기 금지" 같은 코드 규칙은 테스트가 아니라 별도 규칙 검사(린트) 스크립트에 둔다.
- **왜:** 소스 글자를 읽는 테스트는 동작이 같아도 코드를 옮기면 실패해 구조 정리를 막고, 줄만 남으면 동작이 깨져도 통과한다.
- **적용 사례:** 한 앱에서 메뉴·화면 연결을 앱 없이 싸게 확인하려던 소스 글자 테스트가 122개 파일에 쌓였다. 코드를 다른 파일로 옮기기만 해도 동작은 그대로인데 실패해 구조 정리를 막았다.
- **어떻게:** 이미 있는 것은 기능 테스트로 바꾸거나, 같은 것을 보는 기능 테스트가 있으면 지운다(예: 이름 바꾸기 의도를 부르면 파일 이름이 바뀌고 열린 글이 디스크에 저장돼 있다). 남은 수를 세어 줄어들기만 하게 막고 0 까지 줄인다.
