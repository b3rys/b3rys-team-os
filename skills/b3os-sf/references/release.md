# 출시 — 검증, 채널 보고, 빌드 전달

## 출시 원칙

검사가 머지와 출시를 막는다. 검사가 흔들리면 검사를 먼저 고치고, 만든 AI와 다른 모델·도구의 AI가 리뷰한다. 팀장은 머지 승인과 실사용을 확인한다. 잰 것과 못 잰 것을 분리하고, 못 잰 것은 팀장 손 검증으로 넘긴다.

채널별 정확한 모양은 [`channel-formats.md`](channel-formats.md)가 정본이다. 텔레그램 정리는 상태별 구획과 항목별 상태 아이콘으로 두 번 스크롤 안, todo는 영역·버전 머리와 연속 번호로 한~두 화면, 빌드 전달은 한 화면, 진행 알림은 무엇→어디→다음의 2~5줄로 쓴다. 슬랙은 `b3os-slack-format`, 팀버스는 태그와 결론·근거, 저장소 글은 `b3os-github-workflow`의 핵심 3~5줄을 따른다.

## 빌드 전달 때 같은 묶음으로 할 일

빌드·공증 검사를 기다리는 동안 아래 문서 작업을 별도 브랜치에서 준비하고, 빌드가 끝나면 합친다.

1. **요청 대조표:** 팀장 요청 원문별로 반영·보류를 한 줄씩 쓰고, 요청 밖 변경은 `[내부]`로 분리한다. 사용자에게 설명하는 문장에는 파일·커밋 이름을 넣지 않는다. 도구는 뼈대만 만들며 문장은 사람이 쓴다.
2. **`TODO.md`:** 이번 빌드에 포함된 요청은 원문과 함께 `[x]`, 남은 것과 보류는 이유와 함께 갱신한다.
3. **노하우 문서:** 속도·함정·측정법을 커밋·수치 같은 근거와 함께 쌓는다.
4. **설계 문서:** 구조나 동작 방식이 바뀌었을 때만 바뀐 곳과 이유를 갱신한다.

```text
<앱> <버전> 공증본입니다 (<sha>)

[요청]
1. "<팀장 원문>" — ✅ <바뀐 것 한 줄, 사용자 말로>
2. "<팀장 원문>" — ⏸ <미룬 이유 한 줄>
[내부]
3. <요청 밖 변경> — ✅
꼭 알아야 할 것: <있을 때만>
```

같은 요청이 TODO·커밋·머지 제목에 반복돼도 한 줄로 쓰고 여러 요청을 개수 하나로 접지 않는다. 검사 스크립트의 맥락 없는 요약 문구는 메시지가 아니라 빌드 산출물 파일에만 둔다. 빌드와 함께 요구사항별 자동 시험·앱 화면·못 본 것을 보고하고, 사람이 눌러볼 항목을 명시한다.

출시 채널은 프로젝트에 맞게 `dev`, `beta`, `release`처럼 나누고 각 진입·승격·되돌리기 조건을 기록한다. 자동 업데이트와 산출물 무결성을 확인하며, 플랫폼 서명·공증은 플랫폼별 확장 문서로 분리한다. 출시 게이트 예외는 사람 승인이 필요하다.
