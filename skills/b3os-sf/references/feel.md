# 손맛 — 사용자가 느끼는 품질을 제품에 넣는 법

**핵심:** 손맛을 정의하고 → 판정선을 표 하나에 숫자로 두고 → 동작 원칙을 설계 문서에 적고 → 출고 게이트로 지킨다. 디테일의 기준은 "사용자가 화면·손으로 느끼는가"다.

## 1. 정의 — 팀장과 한 줄로

- 프로젝트 초기에 팀장과 손맛을 한 줄로 정한다.
- 사용자가 가장 자주 하는 동작 3개를 고른다. 이 셋은 매 출고 잰다.

적용 사례: 편집기 앱은 손맛을 반응 속도 · 편집 흐름 · 키보드 흐름 셋으로 정하고, 가장 자주 하는 동작 3개(노트 전환 · 커서 이동 · 글자 입력)를 매 출고 쟀다.

## 2. 측정 — 평균이 아니라 튀는 값

- 사람은 평균보다 튀는 한 번을 버벅임으로 느낀다. p90·p99·max·흔들림(p90−p50)으로 판정한다. 60Hz 화면 기준 한 프레임 16.7ms, 두 프레임 33ms. 실제 판정은 프로젝트 표의 조건별 줄(모드·크기·첫 키 예외·여유)을 따른다.
- 판정선은 표 파일 하나에만 둔다(예: `docs/acceptance/` 아래 표 파일 하나). 코드는 표를 읽는다. 줄마다 기준 커밋과 여유를 적는다(예: `<기준 커밋> <기준값> + <여유>`).
- 몰아치기(키를 연달아): 빠진 키 0, 끝 상태 일치.
- 튜닝 값(기다림·간격·디바운스)은 설정 파일에(프로젝트 설정 파일).
- 판정 방법·래칫: `b3os-verification` §3 Feel · 래칫 ③.

## 3. 원칙 — 테스트의 정답

| 원칙 | 판정 |
|---|---|
| 사용자가 느끼는가 | 느끼면 끝까지, 아니면 10분 안에 범위를 줄이고 다음으로 |
| 의도하지 않은 액션 금지 | 명령의 대상이 사용자 행동(클릭 등)으로 정해지지 않았으면 짐작하지 않고 아무것도 안 한다. 사양에 "없으면 X 로 대신"을 넣지 않는다 |
| 커서는 사용자의 의도를 따른다 | 화면이 바뀌었다고 커서가 스스로 옮기지 않는다. 입력칸이 커서를 받는 경우를 설계 문서에 목록으로 |
| 미세 조정값 리셋 금지 | 팀장이 맞춘 화면값은 제품 결정. 직전 출고본 픽셀 기준으로 고정 |
| 잘되던 기능 회귀 금지 | 오류 수정은 그 오류만. 직전 출고 태그와 실제 키 페이지를 나란히(방법: [`development.md`](development.md#fpfc-를-프로젝트에서-쓰는-법-pm-절차) Check) |
| 동작 원칙 = 테스트의 정답 | "이전 버전이 정답"이 아니라 팀장과 정한 원칙 |
| 가장 많이 쓰는 요소를 먼저 | 실제 문서 모양으로 테스트(예: 표 칸에 코드·굵게·링크·콜론·한글을 섞는다) |
| 핵심 내용 최소 대비 | 본문·라벨·값에 흐린 색·작은 회색 글씨 금지(`b3rys-design`) |
| 사용자 입장의 입력 | 한글 조합·실제 키 입력으로 테스트. fill·curl 통과 ≠ 사용자 입장 |

## 4. 제보에서 출고까지

1. 영상·사진 그대로 받는다 → 재현.
2. 원인 분석은 Find(읽기 전용 분석 에이전트, deep-check 등)에게. 반대 가설 반증.
3. 원칙을 설계 문서에 먼저 적는다(없으면).
4. 깨진 경로만 고친다. 넓은 재작업은 팀장 판단(범위 판단은 팀장이 한다).
5. 기존 테스트 + 재현 테스트로 확인, 모드 출고.

적용 사례: AI 창 포커스 회귀. 제보 뒤 원칙 한 줄을 설계 문서에 먼저 쓰고, 첫 수정안이 새 회귀를 만들어 리뷰에서 막았다. 같은 날 전달본으로 나갔고 포커스 검사의 FAIL 이 24건에서 0건이 됐다.
