# 오픈 준비·사용 통계 — 단계 체크리스트

앱을 바깥 사용자에게 처음 여는 프로젝트(베타·알파 오픈)에서 빠뜨리기 쉬운 단계를 순서대로 둔다. 프로젝트 TODO.md 에 이 목록을 그대로 옮겨 칸마다 `[x]`·`[~]`·`[ ]` 로 관리한다. 앱 쪽 구현 예는 `b3rys/apple-app-shell` 의 `docs/launch-checklist.md`.

★ 팀장 확인이 필요한 단계는 (팀장) 으로 표시했다. 확인 없이 다음 단계로 넘어가지 않는다.

## 1. 기준선

- [ ] 오픈 직전 출고본에 태그를 단다(예: `alpha-open`). 이후 릴리즈 노트·회귀 비교의 기준이 된다.
- [ ] 출고 경로가 끝까지 돈다: 공증본 → 게이트 → 배포 파일(dmg·업데이트 피드) → 업로드 → 실제 공개 주소로 확인 → 롤백 방법(직전 피드 파일 다시 올리기).
- [ ] 업로드(운영 반영)는 (팀장) 승인 뒤에만. 출고본 만들기·전달과 업로드를 나눠서 보고한다.

## 2. 입장 — 초대·대기열

- [ ] 흐름을 화면 순서대로 정한다: 이메일 입력 → 입장 링크 메일 → 링크 누르면 입장. 사람이 손으로 코드를 복사해 보내는 단계는 두지 않는다. (팀장)
- [ ] 자동 발송인지, 목록에서 확인 뒤 발송인지 정한다. (팀장)
- [ ] 메일 발송 설정(발신 주소·DNS 레코드)이 실제로 되어 있는지 DNS 로 확인한다. 기록만 믿지 않는다.
- [ ] 링크는 1회용 고유 토큰, 서버에는 해시만 저장. 링크를 다른 사람이 먼저 쓰면 막을 수 없다는 점을 팀장에게 미리 알린다.
- [ ] 미리보기 봇(메신저·메일)이 링크를 열어도 소모되지 않는지 시험한다.
- [ ] 화면 사진으로 전체 흐름을 팀장에게 보여 주고 확인받는다(말로만 설명하지 않는다). (팀장)

## 3. 릴리즈 노트

- [ ] 정본은 저장소 `docs/release-notes/<버전>.md`. 첫 줄 `# <앱> <버전>`, 아래 `- ` 한 줄씩, 같은 묶음은 한 줄, 명사형, 내부 변경은 뺀다.
- [ ] 출고 커밋에 같이 넣는다. 기준 태그 이전 버전은 만들지 않는다.
- [ ] 사이트 공개 페이지(`/releases`)는 md 추가만으로 생기게. 공개 여부는 (팀장).

## 4. 사용 통계

- [ ] 무엇을 셀지 먼저 적는다: 다운로드 수(서버 다운로드 경로), 사용 수(앱의 업데이트 확인), 누적 설치 수.
- [ ] IP 만으로 세지 않는다. 회사처럼 공인 IP 몇 개로 나가는 곳은 여러 대가 1대로 합쳐진다.
- [ ] 익명 설치 ID: 첫 실행 때 무작위 UUID(v4)를 기기 로컬 설정에 저장하고 업데이트 확인 요청 헤더로 보낸다.
  - 하드웨어 정보(시리얼·MAC)로 만들지 않는다. iCloud 동기화 저장소에 두지 않는다(한 사람의 여러 기기가 합쳐진다).
  - URL 쿼리로 보내지 않는다(프록시 로그에 남는다).
  - ID 저장·전송 실패가 업데이트 확인·앱 시작을 막지 않게 부가 기능으로 분리한다.
- [ ] 서버는 ID 원문을 저장하지 않고 비밀 키로 섞은 값만 저장한다. 그 비밀 키를 바꾸면 누적 수가 리셋된다는 점을 운영 메모에 남긴다.
- [ ] 옛 버전 앱은 기존 방식으로 계속 센다. 한 요청을 두 방식으로 이중 집계하지 않는다.
- [ ] 숫자는 추정치다(누구나 가짜 ID 를 보낼 수 있다). 대시보드에 그렇게 적는다.
- [ ] 시험·탐침이 운영 주소로 요청해 운영 숫자를 부풀리지 않게 한다.
- [ ] 기능 사용 통계(쓴 기능 이름)를 셀 때: 이름 목록은 앱 설정 파일에, 서버는 받을 이름 목록(allowlist)만 받는다. 기록은 기능 시작 지점에서 하루 한 번, 키 입력 경로에는 두지 않는다.
  - 서버가 설치당 하루 한 줄에 기능을 비트(bitmask)로 저장하면, 비트 번호가 과거 행의 뜻이다. 기존 비트의 순서를 바꾸거나, 지운 기능의 비트를 다른 기능에 다시 쓰지 않는다.
  - 기능 추가: 앱 설정에 이름 한 줄 + 시작 지점 기록 한 줄 → 서버 allowlist 와 비트 목록 맨 뒤에 새 비트 하나 → 서버 반영 뒤 앱 출고. 옛 버전 앱은 새 이름을 보내지 않는다.
  - 기능 이름 변경: 비트는 그대로 두고 보내는 이름은 유지, 화면 이름만 바꾼다. 보내는 이름까지 꼭 바꿔야 하면 옛 버전 앱이 남아 있는 동안 서버가 옛 이름도 같은 비트로 받게 해 과거·현재 집계를 잇는다.
- [ ] 반영 순서: 서버 DB 마이그레이션 → 서버 비밀 키 운영 설정 → 서버 코드 배포 → 그다음 앱 출고. 앱이 먼저 나가면 ID 가 버려지고, 키 없이 배포하면 서버가 실패하거나 원문을 다룰 위험이 있다. 단계마다 운영 조회로 확인한다.

## 5. 대시보드·관리 화면 접근

- [ ] 통계 대시보드와 초대 관리 화면은 공개 주소에 두지 않는다. 사설망(tailnet) 안에서만 열고, 통계 키는 서버가 붙인다. (팀장)
- [ ] 공개 서버에서 그 경로를 실제로 지우고, 공개 주소로 열면 404 인지 확인한다(사설망 쪽만 추가하고 공개 경로를 남기는 실수 방지).
- [ ] 비밀 값(통계 키 등)은 파일 경로로만 다룬다. 채팅·버스·문서에 값을 쓰지 않는다. 사람에게 전달할 때는 그 기계에서 클립보드 복사 → 비밀번호 관리자.
- [ ] 앱이 쓰는 경로(다운로드·업데이트 피드·신고)는 접근 제한에서 반드시 뺀다.

## 6. 사용 조건·개인정보 안내

- [ ] 수집하는 것을 한 단락으로 적는다: 앱 버전, 무작위 설치 식별자, IP 저장 여부, 끄는 방법. 문구는 (팀장).
- [ ] "IP 를 저장하지 않습니다" 같은 문장은 서버 코드·DB 열·로그 보관(호스팅 업체 로그 포함)을 전수 확인한 뒤에만 쓴다.
- [ ] 대기열 이메일의 용도와 삭제 시점을 적는다.
- [ ] EU 등 동의가 필요한 지역은 법률 판단으로 따로 확인한다(팀원이 확정하지 않는다).

## 7. 피드백·신고

- [ ] 앱 안 문제 신고 경로가 운영 서버까지 도는지 실제로 확인한다.
- [ ] 팀 소식·답변은 앱의 공용 알림 자리(알약 등)에 등록만 하고, 실패해도 다른 알림·편집에 영향이 없게 한다.

## 8. 오픈 전 검수

- [ ] 오픈 직전 한 번 전체 시험(이유를 말하고 (팀장) 승인, 부하 낮을 때, 다른 작업 멈추고). 시간 목표를 정하고(예: 20분) 넘으면 느린 곳을 줄인다.
- [ ] 실제 공증본을 원본 그대로 실행해 시작 경로를 확인한다(게이트는 이 경로를 안 탈 수 있다).
- [ ] 잘되던 기능이 직전 출고본과 같은지 나란히 비교한다.
- [ ] 여러 기기 설치·복사 설치가 문제없는지 확인한다(기기 제한·로그인 여부를 팀장에게 설명할 수 있게).

## 9. 오픈 뒤

- [ ] 첫날 숫자(다운로드·사용·설치·신고)를 팀장에게 한 번 보고한다.
- [ ] 신고·피드백은 요청으로 받아 BWF(③·④ = FPFC)로 닫고 출고 묶음에 넣는다.

## 10. 웹페이지 공개 전 보안·동작 점검

제품 사이트·랜딩 페이지·Cloudflare Pages/Workers 정적 사이트, 남이 zip 으로 넘긴 페이지를 공개하기 전에 돈다. 항목마다 `확인:` 의 방법으로 닫고 결과를 보고에 적는다.

- [ ] 사이트 CSP(`script-src`·`style-src` 'self' + nonce)와 맞는다: 인라인 `style="…"`, 인라인 이벤트 핸들러(`onclick=` 등), 외부 스크립트는 막힌다.
  - 확인: `grep -nE 'style="|[[:space:]]on[a-z]+="|<script[^>]+src="https?:' *.html` 이 비어 있다. 실제 서버가 내보내는 주소(`file://` 아님)를 열어 콘솔의 CSP 위반이 0건이다.
- [ ] 외부 CDN 에 기대지 않는다: Tailwind Play CDN(실행 시 JIT, 운영용 아님)·jsdelivr/Google 글꼴을 쓰지 않는다. CSS 는 로컬에서 빌드하고 글꼴은 같은 서버에서 준다.
  - 확인: 브라우저 Network 탭에서 제3자 도메인 요청이 0건이다. `grep -nE 'https?://(cdn|fonts)\.' *.html *.css`
- [ ] 개인 이메일·제3자 폼 엔드포인트(formsubmit 등)·추적 스크립트·API 키가 HTML·JS·설정에 없다.
  - 확인: `grep -rlEi '@(gmail|naver|daum|outlook)\.|formsubmit|googletagmanager|gtag\(|api[_-]?key|secret|token' .` 로 파일 이름만 뽑아 열어 본다(`-n`·`-o` 로 일치한 줄·값을 터미널에 찍지 않는다). 시크릿 스캔(`b3os-infra-safety` ⑤)은 값을 가려서(redact) 출력하고, 일치한 값을 로그에 남기지 않는다.
- [ ] 다운로드·주요 링크가 실제로 된다: 다운로드 버튼은 진짜 파일을 준다. 새 탭(`target=_blank`)보다 같은 탭 다운로드를 쓴다. 메뉴·앵커 링크가 목적지에 닿고 약관·개인정보 링크가 열린다.
  - 확인: `curl -sIL <다운로드 URL>` 이 200 이고 `content-type` 이 파일 형식과 맞다(dmg 는 `application/x-apple-diskimage`). 링크 종류별로 본다: http(s) 와 상대 경로는 페이지 기준 절대 주소로 바꿔 `curl -sIL -o /dev/null -w '%{http_code}' <URL>` 의 최종 응답(리다이렉트 뒤)이 200 이다. `#앵커` 는 브라우저 콘솔에서 `[...document.querySelectorAll('a[href^="#"]')].filter(a=>{const h=a.getAttribute('href').slice(1);if(!h)return false;try{return !document.getElementById(decodeURIComponent(h))}catch(e){return true}}).length` 가 0 이다(빈 `#` 는 페이지 맨 위 링크라 통과, 디코드 실패는 잘못된 링크로 센다). `mailto:`·`tel:` 은 주소 형식만 본다.
- [ ] 캐시로 깨지지 않는다: 새 HTML 이 새 CSS 에 기대면 스타일시트 주소에 버전을 붙인다(`style.css?v=<해시>`). CSS 는 몇 시간 캐시되지만 HTML 은 바로 바뀐다. 인라인 SVG 에는 `width`·`height`·`fill`·`stroke` 속성을 직접 쓴다(CSS 가 없어도 크기가 정상이다).
  - 확인: 배포 뒤 옛 버전을 캐시한 브라우저에서 새로고침 없이 연다. `grep -n '<svg' *.html` 의 각 줄에 `width=` 가 있다.
- [ ] 화면을 눈으로 본다: 데스크톱·모바일 폭, 라이트·다크, 두 언어 사이트면 언어마다. JS 오류와 가로 스크롤이 없다.
  - 확인: 폭 1280·390 에서 캡처하고 콘솔 오류 0건, `document.documentElement.scrollWidth <= innerWidth`. 이전 판과 나란히 비교한다.
- [ ] 리뷰·승인·되돌리기: 저장소 밖 폴더로 올리는 페이지도 배포 전에 리뷰어(Codex)가 본다. 공개 배포는 (팀장) 승인 뒤에만 한다. 직전 버전(배포 ID 또는 직전 폴더)을 남겨 바로 되돌릴 수 있다.
  - 확인: 리뷰 결과와 승인 문장을 보고에 붙인다. 직전 버전 ID 를 적고 롤백 명령이 열리는지 본다.
