# 시작 — 요구, 정본, 프로젝트 뼈대

## 시작 조건과 확인 지점

첫 기능 목록은 팀장 요구 원문을 보존해 만들고 팀장에게 확인받는다. 상세 기획서를 먼저 만들지 않고 기능은 개발하며 붙인다. 초기 설계에는 데이터 모델·ID·저장과 동기화·모듈 경계·보안 경계처럼 나중에 바꾸기 비싼 결정만 담고, 구조 그림과 기술 선택을 팀원 리뷰 뒤 팀장에게 확인받는다.

확인 뒤 저장소, `README.md`, `DESIGN.md`, `FEATURES.md`, `TODO.md`, 지속적 통합(CI), `projects.json` 항목, 칸반 카드와 에이전트 팀을 갖춘 최소 뼈대를 만든다. 첫 PR부터 리뷰한다. 아직 쓸지 모르는 기능을 위한 틀·층·인터페이스는 만들지 않는다.

## 정본은 둘, 뷰는 여럿

| 무엇 | 정본 | 어디 |
|---|---|---|
| 팀장 지시·결함·킵 목록 | `TODO.md` | 프로젝트 저장소 루트 |
| 과제 상태(`plan/doing/done`) | 칸반 `task` 카드 | `team.db` (`b3os-task-loop`) |
| 채널 보고 | 위 둘에서 만든 뷰 | 텔레그램·슬랙·팀버스 |

같은 사실을 두 곳에 다른 값으로 적지 않는다. 보고는 `TODO.md`를 읽어 만든다.

## TODO 목록 규율

1. 팀장 메시지 하나를 항목 하나 이상으로 잡고 요지·KST 시각·메시지 id·사진 경로를 남긴다. 팀장 메시지 묶음마다 피드백 제목을 하나 만든다. 공개 저장소에서는 공개 수위를 맞춘다.
2. 상태는 `[ ]` 미착수 · `[~]` 진행중 · `[x]` 완료뿐이며, 바뀌는 순간 갱신한다. Projects 탭은 `[~]`를 진행중으로 세므로 완료 항목을 그대로 두지 않는다.
3. “킵”은 `📌 킵`에 넣고 착수하지 않는다. 킵의 설계를 논의해도 착수 지시는 아니다. 방향이 바뀌면 옛 항목을 지우지 않고 `HH:MM에 뒤집음`을 단다.
4. 검증 중 발견한 결함은 `<담당>이 찾음`으로 구분한다. 시행착오는 저장소가 아니라 개인 메모리나 `SHARED.md`에 적는다.

```markdown
# <프로젝트> — 작업 트래커
`[x]` 완료 · `[~]` 진행중 · `[ ]` 미착수

## 🎯 지향점 · 목표
## 🧱 정해진 구조 · 상시 기준
## 🔄 팀장 피드백 (YYYY-MM-DD HH:MM KST) — <담당> 관리
   - [ ] 항목 — 요지 · 사진 경로 · 원인(후보/확정) · 검증 기준
## 📌 킵 — 착수 안 함
## 🐛 별건 결함 — 검증 중 나온 것
## 🖐 팀장 손 검증 — 시험으로 못 재는 것
```

## 에이전트 팀

프로젝트를 열 때 만드는 역할 N, 판정 역할, 통합 역할과 공통부 주인 한 명을 정한다. 진행 중 역할이 두 일을 맡거나 병목이 생기거나 단계가 바뀌면 팀을 다시 설계한다. 실사용 단계에는 모듈 축 위에 버그·구현·검증 역할 축을 얹고 지시는 한 번에 묶는다. 역할 정의는 프로젝트의 `.claude/agents/`에 둔다. 상세는 [`agent-team-by-domain.md`](agent-team-by-domain.md)와 `b3os-harness-playbook`을 따른다.

## 구현 첫날부터 지킬 구조 규칙

나중에 큰 리팩터링을 하지 않으려면 처음부터 아래를 지킨다. Steno 10-06 구조 정리에서 고친 것을 거꾸로 적은 목록이다(과정: [`structure-refactor.md`](structure-refactor.md)).

| 규칙 | 왜(Steno 에서 실제로 생긴 일) | 첫날 할 것 |
|---|---|---|
| 층을 나눈다: 화면 → 조율 → 기능 타입 → 연결 → 순수 로직. 위층만 아래층을 부른다 | 공용 상태 클래스가 5천 줄까지 커졌다 | 폴더·모듈을 층별로 만들고 순수 로직 모듈은 화면 프레임워크를 import 하지 않게 |
| 조율 클래스는 순서만 정하고 기능 로직을 담지 않는다 | 새 기능이 함수로 계속 들어왔다 | 조율 클래스 함수 수 래칫 |
| 새 기능 = 새 타입 + 설정 키 + 검사 표 한 줄 | 기능 하나가 넓은 검사를 불렀다 | 검사 표(변경 경로 → 검사)를 첫날 만든다 |
| 여러 곳이 같이 쓰는 값은 쓰는 입구 하나 | 알림 한 칸을 9곳이 덮어썼다 | 공유 값은 private set + 의도 함수 |
| 화면은 값을 바꾸지 않고 의도를 부른다 | 화면이 직접 쓰는 곳 25곳 | "화면의 직접 쓰기" 래칫 0 부터 |
| 화면이 순서를 정하지 않는다(저장 → 이름 바꾸기 등) | 17곳이 각자 골라 빠뜨리면 글을 잃었다 | 작업 입구 하나가 순서를 정한다 |
| 같은 일을 두 벌 두지 않는다 | 목록 구현 두 벌 | 대체 구현은 실험 가지에서만 |
| 테스트는 기능을 밖에서 부른다. 소스 글자를 읽지 않는다 | 소스 글자 테스트 122파일 | 소스 글자 테스트 파일 수 래칫 0 부터, 코드 규칙은 린트로 |
| 화면 배선도 실제 화면 객체를 띄워 테스트한다(앱 실행 없이) | 판단 함수만 보는 테스트가 배선 삭제를 못 잡았다 | 네이티브 테스트 대상을 첫날 만든다 |
| 뮤턴트는 버릴 사본에서 | 끊긴 실행이 고장 줄을 원본에 남겼다 | 뮤턴트 실행 도구가 임시 워크트리를 만들게 |
