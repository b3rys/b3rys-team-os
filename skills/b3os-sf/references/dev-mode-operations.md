# 개발 모드 운영 — 구조화, 검사 단계, 공유 기계

공증은 앱 배포 전에 플랫폼 제공자가 앱을 확인해 주는 절차다. 헤드리스 작업은 앱 화면 없이 자동으로 도는 시험·문서 작업이다.

## 원칙

코드를 구조화하면 변경 영향 범위가 좁아지고, 고친 곳 중심의 검사로도 품질을 보장할 수 있어 개발이 빨라진다. 구조화되지 않은 코드는 작은 변경에도 매번 전체 검사가 필요하다. 새 기능은 자기 타입과 자기 설정 파일에 둬 영향 범위를 분리한다.

## 변경 파일로 자동 선택하는 검사 4단계

| 단계 | 무엇을 돌리나 | 언제(누가 정하나) | 대략 시간 |
|---|---|---|---|
| 1 고친 곳만 | 고친 모듈 단위 테스트 | 코딩 중 매번(자동) | 수십 초 |
| 2 고친 곳+핵심 | 1 + 기본 앱 검사 + 공증 | 개발 배포본 기본(표가 자동 선택) | 약 5분(실측 4분 46초) |
| 3 +연관+핵심 | 2 + 공용 파일을 쓰는 기능 검사 | 공용 파일을 건드리면 표가 자동 승격 — 기능 하나가 여기 오면 리팩 신호 | 약 10분(추정) |
| 4 전체 | 모든 테스트·앱 검사 | 큰 리팩·표로 판단 불가·출시 전(사람이 정함) | 약 19분(실측) |

### 선택 방법

- 바뀐 파일을 검사 표 하나에 연결해 단계를 결정한다.
- 표에 없는 파일은 그 파일이 속한 모듈 전체로 넓힌다.
- `Package.swift`, `scripts/ship*.sh`, 공용 설정 같은 뿌리 파일만 전체 검사로 올린다.
- 건너뛴 검사는 이유를 로그에 남긴다.

리팩터링은 목표가 아니다. 개발 모드의 검사표에서는 기능 하나를 추가했는데 검사가 3단계까지 올라가면 리팩 신호다. 기능 머지마다 짧게 구조를 검토하고, 검사표를 근거로 할 때는 이 신호가 있을 때만 리팩터링을 제안한다. 수정 집중·다른 시험 실패·직접 접근 증가·버그 재발 같은 일반 구조 신호는 [`development.md`](development.md#구조-가드)에서 따로 다룬다.

## 관측된 속도와 하한

개발 배포 검사에서 매핑표 선택과 전달 뒤 자동 재검사 중지를 함께 적용한 사례는 19분에서 4분 46초로 줄었다. 플랫폼 공증에 약 4분이 걸려 그보다 아래로는 줄이기 어려웠다. 이 수치는 해당 사례의 실측이며 모든 프로젝트의 보장값이 아니다.

## 공유 기계 순번

여러 프로젝트가 한 기계를 공유하면 긴 개발 검사가 뒤 작업도 밀어낸다. 무거운 검사·빌드·시간 측정은 기계 전체에서 같은 파일 잠금을 잡아 한 번에 하나만 돌린다. 개발 모드에서는 배포본을 전달한 뒤 자동 재검사를 끈다. 출시 전 전체 검사는 사람이 명시적으로 정한다.

macOS 예시는 다음과 같다. 플랫폼과 경로는 환경에 맞게 바꾸되, 기계마다 잠금 하나라는 원칙은 유지한다.

```sh
lockf -k -t 1200 /Users/Shared/steno-locks/machine.lock <무거운 명령>
```

잠금은 작업 종료와 함께 풀려야 하며, 하위 작업이 같은 잠금을 다시 잡아 자기 자신을 기다리게 해서는 안 된다. `lockf`가 제한 시간 안에 잠금을 못 잡으면 종료 코드 75로 끝나며, 실패로 처리하거나 측정 신뢰도 경고를 남긴다. 홈 밖의 공유 폴더를 쓰고, 실제 실행 계정마다 `lockf -k -t 0 <잠금 파일> true`로 같은 잠금을 잡을 수 있는지 확인한다.

예를 들어 macOS 공유 폴더는 `/Users/Shared/steno-locks`, 그룹은 `steno-locks`, 권한은 `2775`로 둘 수 있으며 실행 계정은 모두 그 그룹의 멤버여야 한다. 폴더·그룹은 관리자가 한 번 설정하며, Steno 예시에서는 `scripts/ci-runner-setup.sh`가 맡는다. 이 스크립트를 실행하기 전에는 공유 폴더가 없다. 현재 Steno의 `scripts/lock-lib.sh`처럼 `ship`·`after`·`ci` 역할별 잠금 파일을 직접 만들고 지우는 구현은 기계 전체 잠금과 다른 상태이므로, 여러 프로젝트가 공유할 때는 하나의 `machine.lock`으로 옮겨야 한다. Linux에서 가능한 검사는 GitHub의 Linux 검사로 보내 공유 macOS 기계의 부하를 줄인다.

## 대기 시간 겹치기

앱 검사나 공증처럼 기계·외부 서비스의 완료를 기다리는 동안에는 문서 정리, 요구사항 대조표 작성, 헤드리스 시험 등 독립 작업을 겹쳐 돌린다. 예: 앱 공증이 끝나기를 기다리는 동안 요구사항 대조표를 쓴다. 서로 의존하지 않는 일을 순차로 기다리지 않는다.

## 배포본 전달
