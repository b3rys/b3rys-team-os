# 개발 모드 운영 — 구조화, 검사 단계, 공유 기계

## 원칙

코드를 구조화하면 변경 영향 범위가 좁아지고, 고친 곳 중심의 검사로도 품질을 보장할 수 있어 개발이 빨라진다. 구조화되지 않은 코드는 작은 변경에도 매번 전체 검사가 필요하다. 새 기능은 자기 타입과 자기 설정 파일에 둬 영향 범위를 분리한다.

## 변경 파일로 자동 선택하는 검사 4단계

| 단계 | 검사 범위 | 쓰는 때 |
|---|---|---|
| 1 | 고친 곳만 | 코딩 중 빠른 피드백 |
| 2 | 고친 곳 + 핵심 | 개발 배포본의 기본값 |
| 3 | 고친 곳 + 연관 + 핵심 | 공용 파일을 건드리면 자동 승격 |
| 4 | 전체 | 큰 리팩터링·영향 판단 불가·출시 전; 사람이 정함 |

변경 파일과 검사 매핑표가 단계를 자동 선택해야 한다. 공용 파일처럼 영향 범위가 넓은 변경은 사람이 기억해 올리지 않고 자동으로 3단계로 승격한다.

## 관측된 속도와 하한

개발 배포 검사에서 매핑표 선택과 전달 뒤 자동 재검사 중지를 함께 적용한 사례는 19분에서 4분 46초로 줄었다. 플랫폼 공증에 약 4분이 걸려 그보다 아래로는 줄이기 어려웠다. 이 수치는 해당 사례의 실측이며 모든 프로젝트의 보장값이 아니다.

## 공유 기계 순번

여러 프로젝트가 한 기계를 공유하면 긴 개발 검사가 뒤 작업도 밀어낸다. 무거운 검사·빌드·시간 측정은 기계 전체에서 같은 파일 잠금을 잡아 한 번에 하나만 돌린다. 개발 모드에서는 배포본을 전달한 뒤 자동 재검사를 끈다. 출시 전 전체 검사는 사람이 명시적으로 정한다.

macOS 예시는 다음과 같다. 플랫폼과 경로는 환경에 맞게 바꾸되, 기계마다 잠금 하나라는 원칙은 유지한다.

```sh
lockf -k -t 1200 /Users/Shared/steno-locks/machine.lock <무거운 명령>
```

잠금은 작업 종료와 함께 풀려야 하며, 하위 작업이 같은 잠금을 다시 잡아 자기 자신을 기다리게 해서는 안 된다. `lockf`가 제한 시간 안에 잠금을 못 잡으면 종료 코드 75로 끝나며, 실패로 처리하거나 측정 신뢰도 경고를 남긴다. 홈 밖의 공유 폴더를 쓰고, 실제 실행 계정마다 `lockf -k -t 0 <잠금 파일> true`로 같은 잠금을 잡을 수 있는지 확인한다.

예를 들어 macOS 공유 폴더는 `/Users/Shared/steno-locks`, 그룹은 `steno-locks`, 권한은 `2775`로 둘 수 있으며 실행 계정은 모두 그 그룹의 멤버여야 한다. 폴더·그룹은 관리자가 한 번 설정하며, Steno 예시에서는 `scripts/ci-runner-setup.sh`가 맡는다. 현재 Steno의 `scripts/lock-lib.sh`처럼 역할별 잠금 파일을 직접 만들고 지우는 구현은 기계 전체 잠금과 다른 상태이므로, 여러 프로젝트가 공유할 때는 하나의 `machine.lock`으로 옮겨야 한다. Linux에서 가능한 검사는 GitHub의 Linux 검사로 보내 공유 macOS 기계의 부하를 줄인다.

## 대기 시간 겹치기

앱 검사나 공증처럼 기계·외부 서비스의 완료를 기다리는 동안에는 문서 정리, 요구사항 대조표 작성, 헤드리스 시험 등 독립 작업을 겹쳐 돌린다. 서로 의존하지 않는 일을 순차로 기다리지 않는다.
