# 개발 모드 운영 — 구조화, 검사 단계, 공유 기계

공증은 앱 배포 전에 플랫폼 제공자가 앱을 확인해 주는 절차다. 헤드리스 작업은 앱 화면 없이 자동으로 도는 테스트·문서 작업이다.

## 원칙

코드를 구조화하면 변경 영향 범위가 좁아지고, 고친 곳 중심의 검사로도 품질을 보장할 수 있어 개발이 빨라진다. 구조화되지 않은 코드는 작은 변경에도 매번 전체 검사가 필요하다. 새 기능은 자기 타입과 자기 설정 파일에 둬 영향 범위를 분리한다.

## 변경 파일로 자동 선택하는 검사 4단계

| 단계 | 무엇을 돌리나 | 언제(누가 정하나) | 대략 시간(한 프로젝트의 실측 예) |
|---|---|---|---|
| 1 고친 곳만 | 고친 모듈 단위 테스트 | 코딩 중 매번(자동) | 수십 초 |
| 2 고친 곳+핵심 | 1 + 기본 앱 검사 + 공증 | 개발 배포본 기본(표가 자동 선택) | 약 5분 |
| 3 +연관+핵심 | 2 + 공용 파일을 쓰는 기능 검사 | 공용 파일을 건드리면 표가 자동 승격 — 기능 하나가 여기 오면 리팩 신호 | 약 10분(추정) |
| 4 전체 | 모든 테스트·앱 검사 | 큰 리팩·표로 판단 불가·출시 전(사람이 정함) | 약 19분 |

### 선택 방법

- 바뀐 파일을 검사 표 하나에 연결해 단계를 결정한다.
- 표에 없는 파일은 그 파일이 속한 모듈 전체로 넓힌다.
- 전체 검사를 요청할 사유(뿌리 파일·공유 모듈·저장 형식·서명/업데이트 경로 등)와 승인 절차는 `b3os-verification` §1b 가 정본이다. 여기서 따로 정하지 않는다.
- 건너뛴 검사는 이유를 로그에 남긴다.

리팩터링은 목표가 아니다. 개발 모드의 검사표에서는 기능 하나를 추가했는데 검사가 3단계까지 올라가면 리팩 신호다. 기능 머지마다 짧게 구조를 검토하고, 검사표를 근거로 할 때는 이 신호가 있을 때만 리팩터링을 제안한다. 수정 집중·다른 테스트 실패·직접 접근 증가·버그 재발 같은 일반 구조 신호는 [`development.md`](development.md#구조-가드)에서 따로 다룬다.

## 관측된 속도와 하한

적용 사례: 개발 배포 검사에 변경 파일 매핑표와 전달 뒤 자동 재검사 중지를 함께 적용하자 19분에서 4분 46초로 줄었다. 플랫폼 공증에 약 4분이 걸려 그보다 아래로는 줄이기 어려웠다. 이 수치는 해당 사례의 실측이며 다른 프로젝트의 보장값이 아니다.

## 공유 기계 순번

여러 프로젝트가 한 기계를 공유하면 긴 개발 검사가 뒤 작업도 밀어낸다. 무거운 검사·빌드·시간 측정은 기계 전체에서 같은 파일 잠금을 잡아 한 번에 하나만 돌린다. 개발 모드에서는 배포본을 전달한 뒤 자동 재검사를 끈다. 출시 전 전체 검사는 사람이 명시적으로 정한다.

macOS 예시는 다음과 같다. 플랫폼과 경로는 환경에 맞게 바꾸되, 기계마다 잠금 하나라는 원칙은 유지한다.

```sh
lockf -k -t 1200 /Users/Shared/<프로젝트>-locks/machine.lock <무거운 명령>
```

잠금은 작업 종료와 함께 풀려야 하며, 하위 작업이 같은 잠금을 다시 잡아 자기 자신을 기다리게 해서는 안 된다. `lockf`가 제한 시간 안에 잠금을 못 잡으면 종료 코드 75로 끝나며, 실패로 처리하거나 측정 신뢰도 경고를 남긴다. 홈 밖의 공유 폴더를 쓰고, 실제 실행 계정마다 `lockf -k -t 0 <잠금 파일> true`로 같은 잠금을 잡을 수 있는지 확인한다.

예를 들어 macOS 공유 폴더는 `/Users/Shared/<프로젝트>-locks`, 그룹은 `<프로젝트>-locks`, 권한은 `2775`로 둘 수 있으며 실행 계정은 모두 그 그룹의 멤버여야 한다. 폴더·그룹은 관리자가 한 번 설정한다(설정 스크립트를 실행하기 전에는 공유 폴더가 없다). 역할별 잠금 파일 대신 기계 전체 잠금 하나(`machine.lock`)로 줄을 세운다. Linux에서 가능한 검사는 GitHub의 Linux 검사로 보내 공유 macOS 기계의 부하를 줄인다.

시간 판정이 걸린 실행(출고 게이트·속도 측정)이 도는 동안은 다른 빌드·전체 테스트·새 에이전트의 앱 작업을 하지 않는다(`nice` 는 CPU 만 낮춘다). 시작 전에 부하(`uptime`)를 적고 결과 줄에도 적는다. 조용한 창 공지는 늦게 닿으므로 측정 전에 팀원 전원의 ack 를 받거나 부하가 내려간 것을 확인하고, 부하가 높을 때 잡은 기준값은 "다시 잴 것"으로 표시한다. 속도 검사는 기능 테스트·공증과 동시에 돌리지 않고 끝난 뒤 혼자 순차로 돌리며, A/B 는 번갈아 재서 상대 비교로 판정한다. 앱 수치는 debug/release 를 명시한다. 공용 기계에서 프로세스 정리는 내가 띄운 PID 만(띄울 때 배열에 저장) 하고 이름으로 `pkill` 하지 않으며, 프로세스 목록은 pid·이름·cwd 만 보고 전체 명령줄은 출력하지 않는다(토큰 노출).

### 공용 맥에서 시뮬레이터 함께 쓰기

절차(잠금 안에서만 실행, 대기·실행 제한 분리, 자기 기기만 켜고 끄기, 키체인 비우기 등)는 b3os-mac-app-shell [`references/iphone-dev-test.md`](../../b3os-mac-app-shell/references/iphone-dev-test.md) 1·8장이 정본이다. 시뮬레이터 테스트·빌드는 위 `machine.lock` 안에서만 돌린다.

## 대기 시간 겹치기

앱 검사나 공증처럼 기계·외부 서비스의 완료를 기다리는 동안에는 문서 정리, 요구사항 대조표 작성, 헤드리스 테스트 등 독립 작업을 겹쳐 돌린다. 예: 앱 공증이 끝나기를 기다리는 동안 요구사항 대조표를 쓴다. 서로 의존하지 않는 일을 순차로 기다리지 않는다.

## 배포본 전달
