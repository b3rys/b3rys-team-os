# 개발 — 반복 순환, 진행 점검, 구조 가드

## 요청마다 도는 순환

`요청 → 만들기 → 검사 → 리뷰 → 머지 승인 → 내보내기 → 보고(실사용 확인) → 배우기`

기본 작업 단위는 10분이다. 큰 과제는 칸반 카드에 다음 행동·재개 시각·대안을 갱신한다. 하네스는 계약 → 모듈 병렬 → 통합 → 아키텍처·검증 → 게이트 → 배포·공증 순으로 운용한다. 30분 이상인 작업은 마일스톤·지연·막힘이 있을 때 두 줄로 보고하고, 보고를 빚졌으면 `expect-report`를 등록한다.

코드·문서는 저장소, 상태는 `TODO.md`와 칸반, 기능별 케이스와 검사 파일의 연결 및 인수 매니페스트는 `docs/acceptance` 같은 검증 근거 폴더에 둔다. 리서치·발표는 `/reports`에 둔다. Projects 탭(`docs/PROJECTS_TAB.md`)은 저장소 Markdown을 보여 주므로 별도 상태 보고서를 만들지 않는다.

## 팀장 실사용 피드백 순환 (시험판 연속 전달)

팀장이 시험판을 쓰며 짧은 지적을 연달아 보낼 때의 기본 흐름이다. Steno 10-09 실측: 5시간 동안 지적 14건을 시험판 6개(0.7.37→0.7.42)로 전달, 한 판의 공증 전달은 약 10분.

1. **받기** — 원문을 TODO 한 줄로 잡고, 팀장에게는 "무엇을 어떻게 바꿀지" 한두 줄로 답한다. 짧은 답("오케이", "2번째")처럼 뜻이 갈리면 가장 그럴듯한 해석으로 진행하되 "아니면 바로 멈춥니다"를 붙인다. 되돌리기 어려운 것만 먼저 묻는다.
2. **원인 확정** — 추정을 원인으로 말하지 않는다. 재서(예: AI 스트림 이벤트 시각표), 헤드리스로 재현하고, 대조군(조건 하나만 다른 경우)을 같이 돌린다. "제품 탓이냐 검사 탓이냐"는 구현자가 아닌 별도 조사자가 재현 시험과 함께 판정한다.
3. **맡기기** — 구현자에게 원문·원인(파일:줄)·원하는 동작·검사 범위(늘리지 말 것)·완료 기준(테스트·사진)을 한 메시지로. 같은 판에 들어갈 후속 지적은 같은 가지에 이어 붙인다.
4. **리뷰** — PM이 diff와 사진을 직접 본다. 한두 줄 빈틈(예: 빈 입력 재전송)은 리뷰어가 바로 고쳐 커밋하고 구현자에게 알린다.
5. **전달** — 공증 시험판 + 보고 4칸 [바뀐 것 · 확인한 것 · 확인 못 한 것 · 되돌리기(이전 판 다시 설치)]. 가짜 응답·한 테마로만 본 것은 "확인 못 함"에 적는다.
6. **배우기** — 반복된 판단은 메모리·스킬로 올린다.

함께 지킬 것:
- **승인은 실행 단계에만** — 기능 가지에서의 수정·검사·커밋은 승인 대상이 아니다. main 머지·배포·게시·키·결제·외부 호스팅만 팀장 승인. 팀원이 근거를 물으면 요청자(PM)와 위임 원문을 밝히고, 받지 않은 개별 승인을 받았다고 쓰지 않는다.
- **공유 기계 슬롯** — 화면을 쓰는 검사는 기계 잠금 하나로 줄 세우고, PM이 시작·끝 시각을 준다. "반납되면 GO" 약속은 그 자리에서 리마인더를 건다. 잠금이 일찍 풀리면 대기 약속부터 처리한다.
- **팀장 부재 중** — 주인을 일 단위로 한 명씩 정하고(착수 전 한 줄 공지), 팀장만 할 수 있는 일(승인·로그인·결정)은 목록 하나에 [무엇 · 왜 · 누르면 되는 것]으로 모은다.

## PM 진행 점검

- 프로젝트를 열거나 재개하면 작업 단위 주기(기본 10분)의 세션 점검을 건다. Claude 예시는 `CronCreate`의 `3,13,…,53 * * * *`이며 세션이 끝나면 사라진다. 별도로 `b3os-scheduler`로 약 30분 주기의 세션 밖 durable 점검을 건다. 이 점검은 PM이 아닌 시스템 발신이 맡고 프로젝트를 닫으면 끈다.
- `git for-each-ref --sort=-committerdate`, `ListAgents`, 공유 자원 점유로 가지별 마지막 커밋 시각과 실제 상태를 본다. 변함이 없으면 PM 세션 터미널에 한 줄만 남기고 팀장·팀원에게 보내지 않는다.
- 10분 동안 움직임이 없으면 담당에게 현재 작업·대기·막힘을 묻는다. 20분 동안 없고 답도 없거나 예고한 종료 시각을 넘기면 기존 가지의 작업을 먼저 찾고, 새 담당에게 넘겨 병렬 재배치한다. 원 담당에게는 넘겨받았다고 알리고 미커밋분을 커밋해 SHA로 넘기게 한다. 오래 도는 측정·출시 검사·빌드는 움직임으로 친다.
- 끝난 가지는 바로 리뷰·통합·검사로 넘기고, 공유 자원 대기열은 PM이 정한다. 세션 밖 점검은 마지막 PM 점검 기록 시각, 20분 넘은 가지·카드가 인계 없이 남았는지, 끝난 가지가 다음 단계로 안 넘어갔는지를 잰다. 어긋나면 먼저 PM에게 알리고 한 주기 뒤에도 그대로면 팀장에게 알린다.

## 구조 가드

초기에는 속도와 기본 구조를 우선한다. 틀은 쓰는 곳이 둘 이상이거나 지금 기능이 바로 쓸 때만 만든다. 실험 기능은 기능 플래그 뒤에 둔다.

문서만·기계적 수정이 아닌 하네스에는 구현자와 별도의 읽기 전용 아키텍처 담당을 두며, 가능하면 다른 런타임·모델을 쓴다. 착수 전에는 기능의 자리, 본체 분기, 선행 리팩터링, 과설계를 보고, 머지 전에는 자리·분기·중복을 다시 본다. 맞는 확장 자리가 없으면 가장 가까운 곳에 두고 두 번째 쓰임이 생길 때 경계를 만든다. 결과에는 자리·단계·안 만든 것을 짧게 남긴다. 문서 모양 예시는 `docs/proposals/note-type-handler.md`다.

리팩터링 신호는 같은 파일·함수 수정 집중, 한 버그 수정이 다른 시험을 깨뜨림, 같은 값의 여러 직접 접근, 같은 버그 재발이다. 기준은 줄 수가 아니라 사이드 이펙트이며 파일·함수 줄 수는 신호로만 보고하고 검사 실패 조건으로 쓰지 않는다. 여러 구역이 같은 값을 직접 쓰는 수를 주 기준으로 삼고, 값마다 입구 하나를 목표로 한다. 직접 접근이 늘면 테스트 실패로 드러나게 한다. 한 구역의 뮤턴트가 다른 구역 시험을 깨뜨리면 경계를 나누고, 한 상태를 필드 셋 이상 조합으로 판단하면 상태 하나와 전이표(`reduce`)로 바꾼다.

리팩터링 의견에는 실제 발생 횟수, 미실행 시 영향, 비용을 적는다. 시점은 PM이 정하고 기능 작업 중에는 막힐 때만 끼어든다. 구조 기준의 정본은 `b3os-ai-code-safety`의 `Phase 1`이다. 프로젝트 PR 검증도 `b3os-ai-code-safety`, 증명 방법·래칫·러너는 `b3os-verification`을 따른다. 뮤턴트 양쪽을 재고, 화면은 사진에서 판정하며, 소스 진단은 재현 전까지 후보로만 쓴다.
