# 개발 — 요청 하나 = BWF, 진행 점검, 구조 가드

## 요청 하나 = BWF

요청 하나는 `b3os-bwf` 6단계로 닫고, ③ 실행 · ④ 검증 칸은 FPFC(Find · Pick · Fix · Check) 역할이 맡는다(역할 · 입구 · 끝 조건은 `b3os-bwf`). 소프트웨어 용어로는 만들기 = Fix, 리뷰 = Find, 검사 = Check 다. 머지 승인 · 내보내기는 ④ 를 통과한 뒤의 승인 게이트, 보고(실사용 확인)는 ⑤, 배우기는 ⑥ 이다.

기본 작업 단위는 10분이다. 큰 과제는 칸반 카드에 다음 행동·재개 시각·대안을 갱신한다. 하네스는 계약 → 모듈 병렬 → 통합 → 아키텍처·검증 → 게이트 → 배포·공증 순으로 운용한다. 30분 이상인 작업은 30분마다 두 줄(어디까지·다음 무엇)을 팀장 채널로 먼저 보내고(팀장 채널이 30분 넘게 비면 안 된다), 마일스톤·지연·막힘과 검증·공증 시작 시점도 알린다. 보고를 빚졌으면 `expect-report`를 등록한다. 전달은 끝이 아니다 — 전달하는 같은 턴에 TODO 에서 다음 과제를 골라 붙이고 한 줄로 알린다.

코드·문서는 저장소, 상태는 `TODO.md`와 칸반, 기능별 케이스와 검사 파일의 연결 및 인수 매니페스트는 `docs/acceptance` 같은 검증 근거 폴더에 둔다. 리서치·발표는 `/reports`에 둔다. Projects 탭(`docs/PROJECTS_TAB.md`)은 저장소 Markdown을 보여 주므로 별도 상태 보고서를 만들지 않는다.

## FPFC 를 프로젝트에서 쓰는 법 (PM 절차)

요청 하나(버그·불편·작은 기능)를 BWF 로 닫을 때 PM 이 밟는 절차다. 팀장이 한 줄·사진·영상으로 보내면 시작한다. 역할 정의와 입구는 `b3os-bwf` 「③·④ 칸의 역할」을 따른다: 수정·버그는 Find 부터, 새 기능은 Fix(만들기) → Find(리뷰) → Pick → Fix → Check. 이 절차는 SF 4 만들기·리뷰 · 5 시험·검증 안에서 돈다. 결과는 7 출고 묶음에 모이고, 배운 것은 8 운영·지식으로 간다. 바꾸기 비싼 결정(데이터 모델·저장 형식·모듈 경계)을 건드려야 하면 멈추고 2 설계 · 3 구조 잡기로 올라간다([`start.md`](start.md) · [`structure-refactor.md`](structure-refactor.md)). 각 단계의 '끝:' 줄을 모두 만족한 뒤 다음 단계로 간다.

Fix 를 맡은 AI 와 Find · Check 를 맡은 AI 는 서로 다르다. Find · Check 는 파일을 고치지 않는다. PM 이 실행 과제를 혼자 끝내지 않는다. 구현 담당과 나누고 서로 다른 런타임·모델이 교차로 본다. 분담은 PM 재량이며, 넘기는 설명이 일보다 크면 직접 한다.

크기별 인원:
- 버그·작은 기능: 분석 1 + 구현 1 + PM 리뷰. PM 이 직접 Fix 를 하면 Check 는 다른 AI 가 맡는다.
- 스킬·문서 PR: 만든 쪽과 다른 모델이 리뷰한다.
- 큰 기능·여러 구역에 걸친 리팩토링: 하네스(구현 여럿 + 아키텍처 담당 + 판정). `b3os-harness-playbook`

1. **받기** (BWF ① · ②)
   - 팀장에게 받았다는 것과 다음에 할 일을 한 줄로 바로 답하고, 원문 그대로 `TODO.md` 에 `[~]` 로 올린다.
   - 고치기 전에 신고 원문을 찾아 읽는다(내 요약 한 줄이 원문을 대체하지 못한다). 무엇이 어디서 안 되는지 한 줄로 정리한다(어떤 모드·어떤 대상 종류·어떤 이동 경로). 캡처·영상이면 대상 종류를 먼저 적고 "○○에서 △△ 하면 □□ 로 바뀐다" 한 줄로 되짚은 뒤 진행한다.
   - 짧은 지시의 대상이 둘 이상 가능하면 "○○인가요, △△인가요?" 한 줄로 확인하고, 확인 전에는 담당의 진행 중 작업을 건드리지 않는다. 지시가 단순한 해석과 복잡한 해석으로 갈리면 단순한 쪽을 택하고, 요청 없는 기능·동작은 넣지 않는다.
   - 확정된 예전 결정과 어긋나 보이면 번복으로 읽지 말고 기존 결정 안에서 먼저 해석한다. 그래도 갈리면 추천안을 A 로 둔 A/B 를 한 번 묻는다. 팀장이 어느 쪽이 좋으냐고 되물으면 추천안과 이유 한 줄을 알리고 그 안으로 진행한다.
   - 신고자에게는 재현에 꼭 필요한 사실 하나만 묻는다. 진단 명령을 돌려 달라는 요청은 최후 수단이며, 필요하면 한 번에 묶어 부탁한다.
   - 끝: 답장 · TODO 줄 · 범위 한 줄(또는 정해진 안).
2. **Find** (BWF ③) — 원인이 바로 보이면 PM 이, 안 보이면 분석 에이전트(`deep-check` 서브에이전트 등)가 읽기 전용으로 찾는다.
   - 버그: 분석 에이전트에게 질문 하나와 관련 파일·로그를 준다. 받을 것 5가지 — 원인 파일:줄 · 회귀인지(어느 커밋부터) · 같은 증상이 나는 다른 경로 · 가장 작은 수정 방향 한 가지 · "사용자가 실제로 이렇게 쓴다" 테스트 한 줄. 확인한 사실과 추정을 나눠 적게 하고, 빠진 항목이 있으면 다시 묻는다. 팀장이 범위를 좁혀 주면(예: 한 모드에서는 정상) 그 에이전트에게 바로 전한다. 예외를 막는 분기를 더하기 전에 "이 상태에서 이 사건이 오면 무엇이 되어야 하나"(사건→상태 표)부터 본다 — 상태 규칙을 바로잡으면 예외가 사라지는 경우가 많다.
   - 새 기능: 만들기(Fix) 전에 바꿀 곳(파일)과 영향받는 기존 기능·동작을 한 줄씩 적어 Fix 과제의 완료기준에 넣고, 만든 뒤의 Find(리뷰)가 그 목록으로 본다. 기존 동작 위에 새 조작을 얹으면 기존 동작이 느려지지 않는지부터 잰다.
   - 아키텍처 리뷰 · 깊은 원인 분석(Find)은 상위 모델 + 높은 추론, Fix 와 Check 는 일반 모델 + 중간 추론이다. 같은 기능 수정이 두 번 실패하거나 고친 뒤 다른 곳이 깨지면 증상 막기를 멈추고 Find 를 다시 한다(같은 판단을 하는 곳이 몇 군데인지부터).
   끝: 원인(또는 바꿀 곳) 파일:줄 + 영향받는 기존 기능 + 수정 방향.
3. **Pick** (BWF ③) — 범위와 이번에 뺄 것을 고른다. 값·정도·이름·배치는 담당이 정하고 근거를 한 줄 적는다. 팀장에게는 방향·우선순위·되돌리기 어려운 선택만 묻는다. 방향이 정해진 뒤에는 확인용 시안을 끼우지 않고 구현 → 검증 → 전달한다. 구현 담당은 `agents.json` 역할로 정한다(담당이 밀리면 PM 이 나눠 직접 구현한다. 밀림 기준은 움직임 없음 10분 → 담당에게 질문, 움직임 없음 20분 또는 예고 시각 초과 → 이관이다. 먼저 원 담당과 요청한 사람에게 이관을 알린다). 원인과 다음 단계(누가 고치는지, 다음 출고 묶음에 넣는다)를 쉬운 말로 팀장에게 보낸다. 끝: 범위 · 뺄 것 · 담당 · 보낸 메시지 id.
4. **Fix** (BWF ③) — 과제 하나 = 메시지 하나 = 스레드 하나로 구현 담당에게 보낸다. 메시지에 넣을 것:
   - 증상(팀장 원문·시각) · 원인과 위치(파일:줄) · 참고할 비슷한 기존 코드
   - 할 일 = 가장 작은 수정 · **이번에 하지 않을 것**(범위 밖이거나 바꾸면 안 되는 기존 동작)
   - 지킬 조건: 기존 기능 무영향. 속도 — 화면 조작·입력 같은 기본 반응 속도가 전과 같아야 하고, 무거운 계산은 필요한 순간에만 한다. 텍스트·설정값은 코드 밖.
   - 변형 표(기능이 달라질 수 있는 축 — 모드·상태·위치 등 — 과 칸마다 기대값): 기대값은 사양에서 가져오고 구현 결과로 굳히지 않는다. 구현 담당이 표 전체 결과를 보고한다.
   - **고정 완료 조건**: 테스트마다 "사용자가 실제로 이렇게 쓴다" 한 줄 · 바뀐 영역만 `--filter` 테스트 통과 · 다음 출고의 기준 브랜치 최신 커밋(sha 를 적는다) 위 새 브랜치 · 결과는 커밋 sha 하나로 한 번만 보고
   같은 파일에 수정을 연달아 위임하면 "기준=<앞 커밋/브랜치>"를 적고, 결과를 받으면 앞 수정이 살아 있는지 diff 로 직접 확인한다(겹치면 두 번 머지하지 말고 하나로 접게 한다). 선행 결과에 기대는 과제는 선행 sha 를 보고받은 뒤에 보낸다(미리 보내야 하면 "선행 작업 사본 읽기·수정 금지, 새 작업 사본에서"를 적는다). 팀장과 사양을 주고받는 중이면 담당에게는 "[멈춤] 사양 확정 대기" 한 건만 보내고, 확정되면 요구 원문 + 최종안 하나를 한 번에 보낸다. 양측 안이 갈리면 조율자가 근거와 함께 먼저 판정해 양쪽에 같은 지시를 보내고, 새 증거나 팀장 지시가 없으면 번복하지 않는다. 구현 담당이 자기 기능의 앱 검사까지 만들어 돌린 뒤 보고하게 지시한다.
   보낸 뒤 `expect-report.sh --thread <과제 스레드>` 로 리마인더를 건다. 사양을 보충할 일이 생기면 같은 스레드에 한 번만 보낸다. 끝: 전달 확인 + 리마인더.
5. **Check** (BWF ④) — 받은 커밋을 만든 AI 와 다른 리뷰어가 읽고, 바뀐 영역 테스트와 그 영역 실앱 검사를 돌린다(앱이 없으면 실제 사용 경로를 한 번 실행). 읽기·재현만 하고 고치지 않는다. 예전 기능이 그대로인지 직전 출고 태그와 나란히 비교한다: 고친 빌드와 직전 출고본을 같은 기계·같은 조건(같은 앱 검사 페이지·실제 키 입력)으로 돌려 결과를 견주고, 통과 = 요청한 변경 밖의 차이가 0이다. 직전에 통과했는데 지금 실패하면 구현 담당의 설명과 상관없이 회귀다. 직전 출고본이 없는 첫 출고는 비교를 생략하고 그 사실을 보고에 적는다. 구현 담당과 다른 AI 가 변형 표를 통합 커밋에서 다시 재고, 속도 요청이 와도 이 단계를 빼지 않고 범위를 줄인다. PM 은 같은 커밋을 한 번 더 읽고, 새로 의심되는 자리는 그 한 가지만 같은 스레드에서 구현 담당에게 다시 확인한다. FAIL 은 PM 이 증거(사진·숫자)를 직접 열어 판정한 뒤 옮긴다. 앱 창 확인이 끝나기 전에는 전달하지 않는다(먼저 줄 때는 "미확인"을 본문에 명시).
   결과는 깨짐 / 구조 / 개선으로 나눈다. Check 미달이면 원인(시험·환경·제품)부터 가린 뒤 Find 로 돌아가고, 제품의 깨짐과 Pick 이 고른 개선만 Fix 로 간다. 구조는 리팩터링 신호로 `TODO.md` 에 적고 시점은 PM 이 정한다([구조 가드](#구조-가드)).
   통과하면 `b3os-github-workflow` 의 머지 절차로 넘기고, 리마인더는 같은 스레드로 `--cancel` 한다. 끝: 깨짐 / 구조 / 개선 결과와 머지된 sha.
6. **묶기·배우기** (BWF ⑤ · ⑥) — 수정마다 곧바로 출고하지 않는다. `TODO.md` 의 다음 출고 묶음 줄(없으면 만든다)에 넣고, 묶음 출고 시점은 팀장께 한 번 확인한다. 팀 내부 전달은 승인 없이 하고, 공개 업로드·full 은 팀장 승인을 받는다(`b3os-verification` §1b). 앱이 멈추거나 데이터가 깨지는 급한 버그만 hotfix 출고로 따로 묻는다. 사용자에게 가는 전달본은 목표 기준을 채운 최종본 한 번이다(중간 출고는 팀 안 검증용). 출고 절차는 [`release.md`](release.md). 버그 보고에는 ① 원인 커밋·부작용 ② 테스트가 왜 못 잡았나(어느 층을 쟀나) ③ 구조 대책을 넣고, ③이 검사나 표의 새 칸으로 남아야 완료다. 기능 문서(FEATURES 등)와 TODO 를 갱신하고, 같은 지적이 두 번째면 장치(테스트·검사·훅)로 막는다(TODO 줄 끝에 `(재지적 n회)`). 끝: 묶음 줄에 들어갔다 · 문서 갱신 커밋.

적용 사례: 보기 모드에서 링크로 노트를 오갈 때 스크롤 위치가 어긋나고, 이동 중 흰 화면이 깜빡였다.
- Find · Pick: 읽기 전용 분석 에이전트가 스크롤의 원인 위치(파일·줄)와 가장 작은 수정 방향 한 가지를 찾았고, PM 이 흰 화면의 원인 두 가지(빈 페이지를 먼저 한 번 읽음 · 읽는 동안 가림막이 없어 기본 흰 바탕이 비침)를 찾았다. 가장 작은 수정 둘만 골랐고 변환 속도·디자인은 뺐다. 바꾸기 비싼 결정이 아니라서 2 설계는 건너뛰었다.
- Fix · Check: 구현 담당에게 과제 하나·스레드 하나로, 잴 수 있는 완료 조건("이동 중 흰 화면 0", "링크로 갔다가 되돌아오면 같은 자리")과 함께 보냈다. 구현 담당이 고치기 전·후 앱을 각각 재고, PM 은 예전 기능(앞서 넣은 스크롤 기억 · "원문 → 보기" 전환 자리)이 그대로인지 다시 본다. 앞선 스크롤 수정 때는 PM 이 커밋을 읽다가 전환 자리와 충돌할 수 있음을 찾아 그 한 가지만 다시 확인했다. Check 는 읽기·재현만 한다.
- 출고 · 운영·지식: 바로 내보내지 않고 다음 출고 묶음에 넣었고, "화면이 바뀔 때 기본 바탕이 비치지 않게 읽는 동안 이전 화면을 가린다"를 일반 규칙 후보로 남겼다.

## PM 진행 점검

- 프로젝트를 열거나 재개하면 작업 단위 주기(기본 10분)의 세션 점검을 건다. Claude 예시는 `CronCreate`의 `3,13,…,53 * * * *`이며 세션이 끝나면 사라진다. 별도로 `b3os-scheduler`로 약 30분 주기의 세션 밖 durable 점검을 건다. 이 점검은 PM이 아닌 시스템 발신이 맡고 프로젝트를 닫으면 끈다.
- `git for-each-ref --sort=-committerdate`, `ListAgents`, 공유 자원 점유로 가지별 마지막 커밋 시각과 실제 상태를 본다. 변함이 없으면 PM 세션 터미널에 한 줄만 남기고 팀장·팀원에게 보내지 않는다.
- 움직임 없음 10분 → 담당에게 현재 작업·대기·막힘을 묻는다. 움직임 없음 20분(또는 예고 시각 초과) → 이관: 기존 가지의 작업을 먼저 찾고, 새 담당에게 넘겨 병렬 재배치한다. 원 담당에게는 넘겨받았다고 알리고 미커밋분을 커밋해 SHA로 넘기게 한다. 오래 도는 측정·출시 검사·빌드는 움직임으로 친다. 10분 점검은 커밋만 보지 말고 도는 실행의 경과 시간도 본다 — 평소값의 2배를 넘으면 CPU 를 확인하고 0% 면 멈춰 원인부터 찾는다. 전체 스위트는 한 번에 하나, 다른 에이전트가 빌드하지 않을 때만 돌린다.
- 끝난 가지는 바로 리뷰·통합·검사로 넘기고, 공유 자원 대기열은 PM이 정한다. 세션 밖 점검은 마지막 PM 점검 기록 시각, 20분 넘은 가지·카드가 인계 없이 남았는지, 끝난 가지가 다음 단계로 안 넘어갔는지를 잰다. 어긋나면 먼저 PM에게 알리고 한 주기 뒤에도 그대로면 팀장에게 알린다.

## 구조 가드

초기에는 속도와 기본 구조를 우선한다. 틀은 쓰는 곳이 둘 이상이거나 지금 기능이 바로 쓸 때만 만든다. 실험 기능은 기능 플래그 뒤에 둔다.

문서만·기계적 수정이 아닌 하네스에는 구현자와 별도의 읽기 전용 아키텍처 담당(상위 모델 + 높은 추론)을 둔다. 설계 판단 전에는 기능의 자리, 본체 분기, 선행 리팩터링, 과설계를 보고, 출고 묶음마다 1회 그 묶음의 diff 전체로 자리·분기·중복과 건드린 기능을 다시 본다. 묶음 리뷰는 고치는 동안 백그라운드로 돌려 출고 시간을 늘리지 않는다. 맞는 확장 자리가 없으면 가장 가까운 곳에 두고 두 번째 쓰임이 생길 때 경계를 만든다. 결과에는 자리·단계·안 만든 것을 짧게 남긴다.

리팩터링 신호는 같은 파일·함수 수정 집중, 한 버그 수정이 다른 테스트를 깨뜨림, 같은 값의 여러 직접 접근, 같은 버그 재발이다. 기준은 줄 수가 아니라 사이드 이펙트이며 파일·함수 줄 수는 신호로만 보고하고 검사 실패 조건으로 쓰지 않는다. 여러 구역이 같은 값을 직접 쓰는 수를 주 기준으로 삼고, 값마다 입구 하나를 목표로 한다. 직접 접근이 늘면 테스트 실패로 드러나게 한다. 한 구역의 뮤턴트가 다른 구역 테스트를 깨뜨리면 경계를 나누고, 한 상태를 필드 셋 이상 조합으로 판단하면 상태 하나와 전이표(`reduce`)로 바꾼다.

리팩터링 의견에는 실제 발생 횟수, 미실행 시 영향, 비용을 적는다. 시점은 PM이 정하고 기능 작업 중에는 막힐 때만 끼어든다. 구조 기준의 정본은 `b3os-ai-code-safety`의 `Phase 1`이다. 프로젝트 PR 검증도 `b3os-ai-code-safety`, 증명 방법·래칫·러너는 `b3os-verification`을 따른다. 뮤턴트 양쪽을 재고, 화면은 사진에서 판정하며, 소스 진단은 재현 전까지 후보로만 쓴다.
