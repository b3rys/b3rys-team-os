# 구조 정리(리팩터링) 과정

**핵심:** 신호가 보이면 앱 전체를 재고 → 위험 순으로 한 덩어리씩 옮기고(동작 변경 0, 뮤턴트로 증명) → 래칫으로 다시 못 무너지게 막는다.

바탕은 SOLID 다(한 타입 한 역할 · 붙여서 확장 · 작은 인터페이스 · 구체 클래스 대신 약속에 기대기). 시간이 지나면 한 클래스에 역할이 쌓이는 것은 정상이고, 그때 리팩한다. AI 팀은 빨리 많이 고쳐서 그 때를 늦게 알아차리므로 구조 숫자로 신호를 받는다.

리팩터링의 목표는 기능 추가와 버그 수정을 쉽고 안전하게 만드는 것이다. 리팩터링 자체가 목표가 되면 안 된다.
이 문서는 언제 시작하고, 어떻게 재고, 어떻게 옮기고, 어떻게 지키는지를 정한다. 사례는 Steno(2026-10-06)다.

용어
- **래칫(ratchet):** 숫자가 늘면 실패하고, 줄면 기준값을 내리게 하는 검사. 구조가 다시 무너지지 않게 막는다.
- **뮤턴트(mutant):** 코드 한 줄을 일부러 고장 낸 사본. 테스트가 그 고장을 실제로 잡는지 증명할 때 쓴다.
- **입구:** 여러 곳이 같이 쓰는 값을 바꾸는 단 하나의 함수.

## 0. 무엇으로 잘됐는지 보나 — 지표 6개

리팩 결과는 이 6칸으로 보고한다. 칸마다 "잰 것 / 구조 근거 / 아직 모름"을 나눈다. 버그 수·운영 속도는 실사용과 같은 수정 비교로만 말한다.

1. 버그가 덜 생기나 2. 고치기 쉬운가 3. 테스트·검증이 쉬운가 4. 운영 속도(요청 → 공증본)가 빨라졌나 5. 다른 팀원이 고쳐도 설계가 유지되나 6. 다시 역할이 쌓이는 때(리팩 냄새)가 숫자로 드러나나

## 1. 언제 시작하나 — 신호

| 신호 | 예(Steno) |
|---|---|
| 기능 하나를 넣는데 넓은 검사(3단계)가 계속 걸린다 | 노트북 수정이 공용 상태 파일을 건드려 저장·큰 파일 검사까지 돌았다 |
| 같은 일을 두 곳에서 한다 | 목록 구현 두 벌 — 고칠 때마다 두 번 |
| 여러 곳이 같은 값을 직접 바꾼다 | 오류 알림 한 칸에 기능 9개가 직접 썼다 |
| 화면이 순서를 정한다 | 이름 바꾸기 전 "편집 중 글부터 저장"을 화면 17곳이 각자 골랐다 — 빠뜨리면 글을 잃는다 |
| 코드를 옮기기만 해도 테스트가 깨진다 | 소스 글자를 읽는 테스트 122개 파일 |

## 2. 재기 — 한 클래스가 아니라 앱 전체

1. 앱 전체 지도를 먼저 만든다: 모듈·타입·크기·누가 누구를 부르나·함께 자주 바뀌는 파일. 한 클래스 안만 보면 문제의 절반을 놓친다(Steno: 클래스 안 15곳을 고쳤는데 밖에 13곳이 더 있었다).
2. 숫자로 "전"을 박는다: 클래스 줄·함수 수, 화면의 직접 쓰기 수, 같은 일 두 벌, 순서를 화면이 정하는 곳, 소스 글자 테스트 수, 복붙 중복.
3. 목표 층을 정한다: 화면 → 조율 → 기능 타입 → 연결 → 순수 로직. 위층만 아래층을 부른다. 화면은 값을 바꾸지 않고 의도만 부른다.

## 3. 옮기기 — 위험 × 자주 건드림 순

- 순서는 "오늘 버그 위험 × 기능이 건드리는 빈도"로 정한다. 글을 잃는 위험(저장 순서)이 먼저다.
- 한 번에 한 덩어리(30~60분). 덩어리마다 완료 기준:
  - 동작 변경 0, 기존 기능 테스트 통과(바뀐 모듈만).
  - 옮긴 동작마다 뮤턴트 하나 이상이 기능 테스트에서 실제 실패.
  - 래칫 숫자는 줄거나 그대로(늘면 까닭을 표에 적는다).
  - 설계 문서와 전/후 표에 한 줄.
- 둘 이상이 나눠 할 때: 기준점(커밋)을 지정하고, 한 사람이 머지한다. 겹친 곳은 머지하는 사람이 두 의도를 다 살려 합친다.

## 4. 테스트 — 소스 글자가 아니라 기능을 밖에서

- 소스 글자를 읽는 테스트는 만들지 않는다. 있는 것은 셋 중 하나로: 같은 걸 보는 기능 테스트가 있으면 삭제 · 없으면 기능 테스트 새로 · 앱을 띄워야만 보이면 앱 검사 단계에 맡김.
- 지우기 전에 증명한다: 지키던 코드 한 줄을 고장 내서 대신 지키는 테스트가 실제로 실패하는지. Steno 에서 "같은 걸 본다"고 적힌 테스트가 판단 함수만 보고 화면 배선은 못 잡는 경우가 실제로 나왔다.
- 아무것도 못 지키면 "빈틈"으로 적고 지우지 않는다.

## 5. 안전 — 끊겨도 잃지 않게

- 뮤턴트는 버릴 사본(`git worktree add --detach`)에서만 돌린다. Steno 에서 실행 도중 재시작으로 고장 줄이 원본에 남은 일이 있었다(셀 실행 요청이 `return` 으로).
- 끊긴 뒤에는 뮤턴트 표의 원본 줄이 각각 정확히 한 번 있는지 세어 잔재를 찾는다. 재시작마다 다시 센다.
- 작은 단위로 자주 커밋한다.

## 6. 지키기 — 래칫

- 구조 숫자를 매 빌드마다 잰다: 조율 클래스 함수 수, 화면의 직접 쓰기 수, 조율자를 아는 기능 파일 수, 소스 글자 테스트 파일 수, 화면이 순서를 고르는 호출 수.
- 늘면 실패. 올려야 하면 그 줄의 까닭 칸을 같이 고친다(리뷰에서 보인다).
- 개발 검사 표의 항상 도는 칸에 넣는다(몇 초).

## 7. 끝 — 교차 검증과 전/후

1. 구조: 지도를 다시 재서 목표 층과 맞는지.
2. 로직: 시작점부터 전체 diff 를 옛 동작과 대조(글·실행에 걸린 곳은 줄마다).
3. 테스트: 지운 테스트마다 대체 검증과 뮤턴트 증명.
4. 이 작업에 안 들어간 검증자(다른 모델 포함)가 같은 범위를 따로 보고 결과를 맞춘다.
5. 전/후 표와 "같은 수정을 다시 했을 때 검사 단계·시간"을 남긴다.
