# Team Learning Log (SHARED.md)

> Status: template
> Role: 팀이 일하며 얻은 교훈을 append-only 로 쌓는 곳. 운영 규칙은 `TEAM-OS.md` 를 본다.
> 공개 릴리스에서는 비워둔 템플릿입니다 — 당신 팀의 교훈으로 채우세요.

## 이 파일을 왜 쓰나

같은 실수를 두 번 하지 않기 위해서입니다. 팀원이 무언가에 걸렸을 때 **원인과 다음에 확인할 방법**을
남기면, 다음 사람이 같은 자리에서 멈추지 않습니다.

AI 팀원은 세션이 바뀌면 맥락을 잃습니다. 이 파일이 **팀의 기억이 사는 곳**입니다.

## 쓰는 방법

- **덧붙이기만 합니다**(append-only). 지난 기록은 고치지 않습니다 — 그때의 판단도 기록의 일부입니다.
- 최신 항목을 위에 둡니다.
- 한 항목은 아래 다섯 줄이면 충분합니다.

```markdown
## YYYY-MM-DD — 한 줄로 요약한 교훈

- 케이스: 무슨 일이 있었나 (증상 · 어디서 · 어떻게 드러났나)
- 교훈: 다음에 무엇을 다르게 할 것인가
- 검증법: 이걸 어떻게 확인했나 / 다음엔 어떻게 확인할 것인가
- 반영처: 어떤 파일·규칙·스킬에 반영했나
- 상태: 관측됨 / 확정 / 보류
```

## 예시 (형식 참고용 — 지우고 시작하세요)

```markdown
## 2026-01-15 — 배포됐다고 동작하는 것은 아니다

- 케이스: 수정을 머지하고 배포까지 했는데 증상이 그대로였다. 서버는 새 코드를 받았지만
  브라우저가 옛 번들을 캐시하고 있었다.
- 교훈: "머지 = 배포 = 동작" 이 아니다. 세 단계를 각각 확인해야 한다.
- 검증법: 배포 후 실제로 서빙되는 산출물에서 바뀐 문자열을 찾는다(로그 말고 결과물).
- 반영처: 배포 절차 체크리스트.
- 상태: 확정
```

## 2026-07-30 — 부정 단정은 "실행이 거기까지 갔다" 를 먼저 단정해야 한다

- 케이스: 셸 스크립트 인수테스트에서 `"경고가 출력되지 않았다"` 류의 단정 9건이 통과했다. 그런데
  실제로는 스크립트가 그 지점에 ★도달하기 전에 죽어 있었다★ — 출력이 아예 없으니 "없다" 는 참이 됐다.
  기능이 죽은 채로 테스트가 초록이었다.
- 교훈: `~가 없다` 를 단정하기 전에 `실행이 그 지점까지 갔다` 를 별도로 단정한다. 준비 단계(설정 로드·
  신원 해석 등)가 성공했는지, 그리고 검사 대상 단계까지 도달했는지를 각각 본다.
- 검증법: 구현을 일부러 되돌려(변이) 테스트가 ★빨개지는지★ 확인한다. 안 빨개지면 그 테스트는
  아무것도 지키지 않는다.
- 반영처: 셸 인수테스트에 준비단계 가드 + 도달 단정 추가.
- 상태: 확정 (하루에 3회 관측)

## 2026-07-30 — 외부 의존을 스텁으로 바꾼 테스트는 그 의존과의 접합부를 검증하지 않는다

- 케이스: HTTP 호출을 스텁으로 바꿔 25건이 전부 통과했다. 라이브에서는 기능이 ★전혀 동작하지
  않았다★ — 요청 URL 한 줄이 틀려서 API 대신 SPA 의 HTML 을 200 으로 받고 있었다. 로직은 다 맞았고
  스텁은 그 접합부를 대신 통과시켜줬을 뿐이다.
- 교훈: 스텁 테스트로 로직을 지키고, ★실제로 1회 실행★ 해서 접합부를 지킨다. 둘 중 하나만으로는
  검증이 아니다. 특히 판정·확인 도구는 ★자기 고장과 정상 동작의 출력이 같아지지 않는지★ 를 본다
  (고장 시 "판정 보류" 로 흘리면 사용자는 고장을 알 수 없다).
- 검증법: 머지 후 실제 환경에서 한 번 쓰고, 결과를 ★출력이 아니라 저장된 상태★ 로 확인한다.
- 반영처: 접합부 재현 스텁(잘못된 응답을 돌려주는 스텁) + 경과시간 단정 추가.
- 상태: 확정
